# 決策紀錄

本文件以白話整理實作合約 [`ARCHITECTURE.md`](ARCHITECTURE.md) 中標記 **[decision]** 的條目，以及其他規格未明說而必須定案的慣例。每一條都寫出：規格怎麼說、問題在哪裡、決定與理由。合約是規範性文件（英文）；本文件只是導讀，兩者不一致時以合約為準。

## D1 畫布 257×182 與片幅 36×24 長寬比不符 → 範例改用 273×182

- **規格**：§4 要求 `canvas_mm` 長寬比必須等於 `frame_mm`，否則回報錯誤；同一節的範例卻給 `canvas_mm = [257, 182]`（JIS B5）配 `frame_mm = [36, 24]`，1.412 ≠ 1.5。
- **決定**：規則優先。驗證拒絕範例的組合（`output.canvas_mm` 錯誤），`examples/basic.json` 改成 `[273, 182]`：3:2、高度不變。
- **理由**：長寬比規則是輸出座標能和相機片幅一一對應的前提；若放寬規則，畫面就得裁切或變形，兩者規格都沒有定義。想用 B5 紙的使用者改片幅（例如 `[36, 25.5]`）即可。

## D2 畫面座標原點在畫幅中心、主點在 shift_mm 處（合約 §2.1）

- **規格**：§2 名詞表說畫面座標「原點在主點」；§5.4 的 K 矩陣卻把主點放在 (u₀, v₀)，表示原點不在主點。兩者只在 `shift_mm = 0` 時一致。
- **決定**：照 K 公式。原點在畫幅中心，主點標記畫在 (u₀, v₀) = `shift_mm` × s，s = `canvas_mm[0] / frame_mm[0]` 是片幅放大到畫布的倍率；JSON、SVG、測試中的所有 `image` 座標與 mm 容差都是**畫布 mm**。
- **理由**：移軸的目的是讓畫面中心不在光軸上，座標原點若跟著主點跑，畫布就不再對稱於原點，SVG 的 viewBox 映射會變得依賴移軸量。

## D3 有向射影幾何（合約 §2.1）

- **規格**：§5 以齊次座標統一有限點與無窮遠點，§7.1 第 5 列要求「任何齊次向量乘以非零常數結果不變」。
- **問題**：受光判定、影子的 w 符號、近平面裁切都是**符號**判定；乘上負常數會翻轉符號，規格的「非零常數」在這些判定上不可能成立。
- **決定**：採有向射影幾何。標準形：有限點 w = +1；方向向量 (d, 0) 指向射線前進方向；點光 (l, 1)；平行光 (l, 0) 且 l 指向光源；受影面 π 以光源為正側（πᵀL > 0）。`normalize_max` 保留符號。§7.1 第 5 列以**正**純量測試所有輸入，正負純量只測試與符號無關的輸出（有限點的影像座標、圓錐曲線矩陣）。
- **限制**：場景文件只含標準形輸入（位置、單位方向），所以這條不變量在輔助函式層級（`shadow_matrix`、`project`、`self_check`、`conic_entry`、`curved.silhouette` …）驗證，無法透過 `render` 端到端驗證。

## D4 作圖線一律是 2D 線段（合約 §2.7）

- **規格**：§5.7 第 1 列：光源在觀者後方時「L′ 仍為有限點（反光點）；作圖線經近平面裁切後繪製」。
- **問題**：3D 線段 LP 有一端在相機後方，近平面裁切後它的影像是從 P′ 往**遠離** L′ 的方向延伸到無窮遠——也就是 2D 線段 L′P′ 的補集；但影子點 S′ 可證明落在 L′ 與 P′ 之間。照規格字面畫，線不會經過 S′。
- **決定**：作圖線永遠是 2D 線段：L′P′ 是涵蓋 L′、P′、S′ 的最短線段（L′ 在無窮遠時取 P′→S′ 向兩端各延伸 20%），F′Q′ 同理，另加頂點垂線 P′Q′；只做畫布矩形（外擴 25%）的齊次裁切。P、S、Q 任一在相機後方的頂點不畫作圖線（計入 `POINT_BEHIND_CAMERA`）。
- **理由**：畫家在紙上畫的就是這條 2D 線；反光點的意義正是「從它拉線到頂點，影子在線上」。

## D5 場景尺度與容差（合約 §2.8）

- **規格**：§5.8「容差 ε = 1e-9 乘以場景包圍盒尺度」，未定義包圍盒含哪些東西。
- **決定**：A 段 `scene_scale_A = max(1, 所有物件網格頂點包圍盒最長邊)`，不含相機（否則 A 段結果會隨相機改變，違反 §7.1 第 2 列「影子與相機無關」）；B、C 段取 `max(scene_scale_A, 含相機位置的包圍盒)`。光源位置一律不計入，否則 §7.1 第 3 列把點光源推到 10⁶ m 外時容差會變成 1e-3 m。長度量的判定（近平面、w_S、點光源受光、地面裁切）用 `tol = 1e-9 · scene_scale`；無因次量（平行光受光、方向判定）用 `tol_dir = 1e-9`。

## D6 L′ 或 F′ 不存在的情況（合約 §2.7）

- **規格**：未提及。
- **決定**：平行光沿受影面法線（正上方的太陽）時 F = foot(π, L) 是零向量：不輸出 `F.<light>` 點、`shadow_vp` 與 `shadow_vp_at_infinity` 皆為 null、不畫 F′Q′、不發 `SHADOW_VP_AT_INFINITY`，自我驗證改為 S′ = Q′。點光源在相機中心時 L′ = P·L = 0：`light_point` 與 `light_point_at_infinity` 皆為 null、不畫 L′P′、不發 `LIGHT_POINT_AT_INFINITY`，自我驗證改為 S′ = P′。
- **理由**：兩者都不是數值退化，而是該量在幾何上不存在；若用捨入誤差算出一個方向再發警告，輸出會不確定。

## D7 無界影子的無窮遠弧（合約 §2.5）

- **規格**：§5.7 第 4 列只說「影子多邊形成為無界區域，裁切到畫面範圍後輸出並標記」。
- **決定**：頂點不低於點光源時，該邊以 w = 0 的**方向頂點** D = (1−t\*)·S_a + t\*·S_b（t\* 使 w_D = 0）取代；在出射方向 D_out 與下一個入射方向 D_in 之間，區域是地面 (x, y) 上由 D_out **逆時針**掃到 D_in 的弧（Δθ ∈ (0, 2π]），並插入中間方向頂點使每段小於 90°（每段 ≤ 60°），因為齊次插值只能涵蓋較短的弧。結果是一個有向齊次多邊形，`unbounded = true`，走完整繪圖管線。
- **驗證**：`tests/test_degenerate.py` 在畫面空間用光線投射比對畫出的多邊形，並以突變測試確認「掃錯方向」會被抓到。
- **修訂**：「下一個入射方向」只在迴圈與光平面相交兩次時是迴圈順序上的下一個；相交四次以上時由交點的角度順序決定，見 D70。

## D8 繪圖管線順序（合約 §2.2）

- **規格**：§5.4「先投影成齊次 3 維向量，在齊次空間對近平面裁切，最後才除以 w」。
- **決定**：每條線段與多邊形固定四步：(1) 在 4D 世界齊次座標對 ν(X) = forward·(x − C·w) − near·w ≥ 0 裁切（Sutherland–Hodgman）；(2) 乘 P；(3) 在 2D 齊次座標對外擴 25% 的畫布矩形裁切（有界矩形不含無窮遠點，所以存活頂點 x̃₃ > 0）；(4) 最後除以 x̃₃。第 3 步對含方向頂點的圖形（無界影子、地平線、作圖線）是必要的。個別點在相機後方時 `image` 為 null、`depth` 照給；L、F 與消失點永遠不裁切、不設 null，只要 |x̃₃| > tol 就直接相除。

## D9 部分埋入地面的物件（合約 §2.3、§2.6）

- **規格**：未提及（只說物件放在地面上時 z = 0）。
- **決定**：頂點在地面下的多面體先被受影面切成實體（`clip_mesh_to_plane`），切面成為實體的一部分；切面不受光，所以它受光側的邊成為光輪廓邊，影子正是地面以上部分的影子（含足印）。地面交點命名 `<obj>.s<k>.<light>`，本身是自己的影子與垂足，不畫作圖線。切面不是封閉流形時退路為逐邊裁切輪廓迴圈。曲面基元的 `OBJECT_BELOW_RECEIVER` 以精確曲面判定（`curved.plane_min`），輪廓迴圈在地面下的部分換成**地面截面受光邊界**的折線（每整圈 64 個取樣點，不進 `conics`），截面退化或截面上沒有受光點時才退回直線弦。
- **驗證**：以光線投射比對（IoU ≥ 0.99），並檢查足印內每個地面點都在影子內。

## D10 圓錐曲線的分類、條件數與取樣（合約 §2.6）

- **規格**：§5.6「橢圓直接寫 SVG ellipse；拋物線、雙曲線以參數取樣成折線」，§11.3「接近退化改為取樣折線並回報警告」。
- **決定**：變換用伴隨矩陣 C′ = adj(H)ᵀ·C·adj(H)，奇異的 H 不會拋例外。分類必須平移不變：以左上 2×2 區塊的行列式符號分橢圓／雙曲線，|det| ≤ 1e-12 為拋物線；退化與條件數在平移到中心（拋物線平移到頂點）並以最大元素正規化後判定，|det| ≤ 1e-12 為退化、條件數 > 1e8 → `CONIC_SAMPLED`。一個距原點 50 m 的 0.3 m 圓必須被判為健康橢圓。近平面裁切與畫布裁切在圓參數上閉式求解（ν(X(θ)) = A cos θ + B sin θ + C）。取樣規則：每整圓 64 段、弧按比例、最少 8 段，段數**四捨五入**（非無條件進位），避免半圓在 §7.1 第 3、4 列的捨入雜訊下段數跳動。精確的圓錐曲線本身在 A、B 段從不取樣（近平面裁切、畫布裁切與 w_S = 0 的交點都在圓參數上閉式求解），圓錐曲線的**可繪圖形**（`polylines` / `arcs` / `ellipses`）只在輸出階段（C 段）取樣；但曲面物件的**填色影子多邊形**（`shadows[].polygons[0]`）與部分埋入物件的地面截面受光邊界（D9）是與相機無關的輪廓的一部分，所以在 A 段就以同一規則取樣成折線（其有限頂點即文件中的地面點 `<obj>.s<k>.<light>`），精確邊界另存於 `shadows[].conics`。
- **球的輪廓圓座標系**：e1 = normalize(n × z)，e2 = n × e1；光源正上方（n ∥ z）時退路改用球的旋轉後局部軸（而非世界 x 軸），讓取樣輪廓隨場景剛體旋轉。

## D11 受影面只接受地面（合約 §2.0）

- **規格**：§1 與 §11.2 說 v1 只有無界地面 z = 0；§4 表格的 `plane(normal, offset)` 寫法看似允許任意平面。
- **決定**：驗證只接受 `normal = [0, 0, 1]`、`offset = 0`（容差 1e-9），其他值回報 `receivers[0].normal` / `.offset` 錯誤。公式本身（M、foot）對任意平面成立，M4 放寬時不必改核心。

## D12 「面與光線平行」的處理（合約 §2.3、§2.9）

- **規格**：§5.7 第 6 列「視為背光，容差內取等號為負」。
- **決定**：|n_f·(l − w·p)| ≤ tol 的面視為「平行」：不受光，並回報 `FACE_PARALLEL_TO_LIGHT`（ids = 物件）。圓柱、圓錐的端面同樣適用。所有判定都是 `> tol` / `< −tol`，中間帶一律算退化側。

## D13 SVG 以標準函式庫輸出，不用 svgwrite（合約 §1）

- **規格**：§8 列 svgwrite 為選用輸出相依。
- **決定**：SVG 以字串組裝（`castplane/output/svg.py`），核心真正只依賴 numpy；PNG 仍以 cairosvg（選用 extra `png`）或 PATH 上的 resvg 柵格化。

## D14 相機慣例（合約 §2.2）

- **規格**：§5.4 只給 K[R | t]，沒定義 R 的建構、滾轉方向、yaw/pitch 形式。
- **決定**：`forward = normalize(target − position)`，`right = normalize(forward × z)`，`up = right × forward`；相機沿 z 看時改用 (0, 1, 0) 當 up 並回報 `CAMERA_LOOKING_ALONG_UP`。滾轉 ρ：`right′ = cos ρ·right + sin ρ·up`，`up′ = −sin ρ·right + cos ρ·up`（正滾轉讓畫面內容順時針轉；測試向量：相機 (0,0,1.5)→(0,5,1.5)、f = 35、畫布 = 片幅 36×24、roll +10°，世界點 (0,5,2.5) 投影到 u = +1.2155 mm）。yaw/pitch 形式：`forward = (−sin yaw·cos pitch, cos yaw·cos pitch, sin pitch)`，yaw 0 朝 +Y、正 yaw 向左轉、正 pitch 抬頭。R 的列是 (right′, up′, forward)，det R = −1 是刻意的（u 向右、v 向上、深度向前為正），不得「修正」。

## D15 警告與輸出的確定性（合約 §2.8、§2.9）

- **規格**：§5.8「退化情況回傳結構化警告，不拋例外」；§8「相同輸入產生位元相同的 JSON」。
- **決定**：警告代碼是封閉清單（13 個，合約 §2.9），每筆 `{code, ids, message}`，去重後依代碼、ids 排序。每個輸出浮點數經 `x + 0.0` 去除 −0.0，以最短往返表示寫出、鍵排序；A、B 段以固定形狀的運算避免累加順序差異；測試同一場景渲染兩次比對位元。

## D16 一致性測試集的比對規則（合約 §4、`tests/conformance/README.md`）

- **規格**：§7.5「所有 image 座標容差 1e-6 mm，warnings 代碼集合必須相同」。
- **決定**：畫面座標與所有可畫圖形（線段、多邊形、折線、弧、橢圓）絕對容差 1e-6 mm；其他數值相對容差 1e-9（下限 1e-9）；非數值完全相等；警告代碼集合相同，另要求 (code, ids) 集合相同。expected 檔只能由 `tools/regen_conformance.py --reason` 產生，每次產生在 `CHANGELOG.md` 追加版本號與原因。

## D17 只換相機重算的效能目標（合約 §4）

規格 §8 的「只換相機重算 < 100 ms」是目標值。兩輪向量化之後，完整渲染約 0.35–0.45 s（達標），
只換相機約 110–130 ms（關閉循環垃圾回收約 90 ms）。剩下的成本是 §6.2 文件本身的 Python 物件
（約 1.5 萬個點、9 千條邊、1.3 萬條作圖線的 dict）與約 12.8 萬個 SVG 座標的格式化，只用 numpy 無法再降。
v1 的決定：保留目標值不改，`benchmarks/README.md` 記錄實測數字，CI 以 `python3 benchmarks/bench.py --gate full`
為閘門，只換相機一項列為已知未達標；收斂方式（更精簡的記錄形狀或編譯式格式化）留到 M7 互動介面時處理，
因為 100 ms 的預算正是為互動預留的。

## D18 自我驗證只對畫出的作圖線做（合約 §2.7）

規格 §5.5 要求 L′P′ 與 F′Q′ 的交點等於直接投影的 S′（1e-6 mm）。屬性測試找到反例：影子點 S 幾乎正好落在相機平面上
（深度 −0.0002 m），它的畫面座標是除以接近零的數，任何 mm 容差都沒有意義；同理，兩條作圖線幾乎平行時交點把捨入誤差
放大 1/sin θ 倍。決定：自我驗證只對作圖線真的會畫出的頂點做（P、S、Q 都在近平面前方，與 §2.7 的畫線條件一致），
這些頂點的畫面座標有界；兩線的正規化交點小於 1e-6 時視為平行，略過並回報 `CONSTRUCTION_CHECK_SKIPPED`。
在相機後方的影子點不畫、不驗證、也不產生警告。一致性測試集因此升到 v2（只有 `degenerate_point_behind_camera` 改變）。


## D19 `LIGHT_BEHIND_CAMERA` 只對點光源發出（合約 §2.7、§2.9）

- **規格**：§5.7 第 1 列「光源在觀者後方：L 的相機深度 x̃₃ < 0 → L′ 仍為有限點（反光點，落在地平線下）」，沒有區分點光源與平行光。
- **決定**：只有點光源（有限的 L）在相機後方時發 `LIGHT_BEHIND_CAMERA`；平行光的方向指向相機後方（forward·d < 0，L′ 是地平線下方的反光點）不發警告。
- **理由**：平行光的 L′ = P·(d, 0) 就是一個方向的普通影像，只要 d 不平行畫面就是有限點；x̃₃ 的正負只說明太陽在相機前半球還是後半球，而作圖線的畫法（涵蓋 L′、P′、S′ 的 2D 線段，D4）在兩個半球完全相同，`light_point` 本身（在地平線下）就告訴畫家這是反光點。這不是退化，所以不發警告（與 D6 同一原則）。`examples/directional.json` 就是這個情況。

## D20 §7.1 第 3 列「點光源退到 10⁶ m 外與平行光相差 < 1e-4 m」在測試域內不恆成立（合約 §4）

- **規格**：§7.1 第 3 列要求點光源沿太陽方向退到 10⁶ m 時，影子與平行光的結果在 1e-4 m 內一致。
- **問題**：屬性測試找到反例：高 2.95 m 的頂點、仰角 20° 的太陽，兩者差 1.001e-4 m，剛好超過容差；而程式庫與閉式解相差只有 1e-15 m。差距是幾何本身，不是數值誤差。
- **推導**：設太陽方向 d = (cos e·â, sin e)（â 為水平方位單位向量、e 為仰角），頂點 P = (p, h)（p 為地面座標、h 為高度）。平行光的影子 S_dir = p − h·cot e·â（影長 h / tan e）。點光源在 L = D·d（從**世界原點**沿太陽方向退 D 公尺），直線 L→P 與 z = 0 的交點是 S_pt = t·p − â·h·D cos e / (D sin e − h)，t = D sin e / (D sin e − h)（頂點在原點正上方時影長為 h·D cos e / (D sin e − h)）。相減得 **S_pt − S_dir = S_dir · h / (D sin e − h)**：點光源的影子是平行光影子以原點為中心、放大 D sin e / (D sin e − h) 倍的位似，差距 δ = h·|S_dir| / (D sin e − h) ≈ h·|S_dir| / (D sin e)，其中 |S_dir| 是影子點到光源退離的原點的距離（頂點在原點正上方時 δ ≈ h² / (D sin e tan e)）。這是精確式，不只是一階近似；反例代入：h = 2.95、e = 20°、D = 10⁶、|S_dir| ≈ 11.6 m → δ = 1.001e-4 m。程式庫對多面體頂點的實測與此式相差 ≤ 1.1e-15 m。曲面物件的作圖點（切線母線端點、輪廓圓象限點）本身也隨光源種類移動（點光源的輪廓與平行光的輪廓在 1/D 的一階不同），其影子另外相差至多「作圖點位移 / sin e」。
- **決定**：不收窄測試分佈（仰角 20–85°、高度至約 3 m 保留），改以推導出的上界當容差：每個具名影子點的差距必須 ≤ max(1e-4 m, 2·δ)，δ = h·|S_dir| / (D sin e − h) + |X_pt − X_dir| / sin e（第二項是作圖點本身的位移，多面體頂點為 0）；多面體頂點的差距向量必須在 1e-9 m 內等於上述位似式；曲面物件的影子多邊形以折線距離比對，上界取物件最高點的 h；而且把光源再退到 10⁷ m 時所有差距必須縮為十分之一（容許 1e-9 m 的捨入下限）。實作在 `tests/test_invariants.py`（`predicted_gap`、`far_point_light_scene`，列 3 的兩個測試）與 `tests/test_property.py`（`assert_point_light_converges`，含面幾乎與太陽平行時、兩種光源的光輪廓差一個無面積的邊緣面的情況：共同點比上界、多出的點必須落在另一邊的影子輪廓上、區域以 IoU 比對）；合約 §4 記為第三個已記錄的例外。
- **理由**：1e-4 m 的固定門檻在規格的測試域邊緣（高頂點、低太陽、離原點遠的影子）必然被幾何差距超過，而「十倍距離差距縮十倍」加上與閉式解一致，才是「點光源收斂到平行光」這條不變量真正要說的事。

# v2 擴充（M4–M8）的決策：D21–D69

以下對應合約 §5（`ARCHITECTURE.md` 第 5 節，v2 擴充）。編號：M4 為 D21–D29（合約 §5.1）、M5 為 D30–D41（§5.2）、M6 為 D42–D48（§5.3）、M7 為 D49–D60（§5.4）、M8 為 D61–D66（§5.5）；D67–D69 是彙整時為了解決五份設計之間的衝突所做的決定（合約 §5.0，標記 **[decision, synthesis]**）。各設計原稿中的章節編號（M4 的 §5.x、M5 的 §6.x、M6 的 M6.x、M7 的 §8.x、M8 的 §9.x）在此一律改寫成合約 §5.1.x–§5.5.x；「規格 §N」指 `docs/spec/spec-v0.1.md`。

## D21 有界受影面的輸入形式：世界座標凸多邊形、一面受影、無界面只能是 `receivers[0]` 的地面（合約 §5.1.1、§5.1.2）

- **規格**：§4 表格「v2 加 bounds（多邊形）」；§9「每面可帶 bounds 多邊形；每面各有自己的 F 與 F′；影子多邊形逐面計算再裁切」。沒有說多邊形用什麼座標、要不要凸、法線朝哪邊。
- **問題**：影子多邊形可能是無界的（含方向頂點）；一般多邊形裁切器需要有界輸入，而且對退化情況不穩。受影面的「正面」又決定了 bounds 的方向、F 的命名與誰受影。
- **決定**：`bounds` 是 ≥ 3 個**世界座標** `[x, y, z]`，每點必須在平面上（1e-9·尺度）、**嚴格凸**（連續三點叉積與 n 同號，且每個轉角的正弦 > 1e-9）、**簡單**（外角總和 = 2π；五角星之類的星形多邊形每個轉角同號但總和是 4π，會被拒絕），順時針輸入與稜柱多邊形一樣靜默反轉成「從正側看逆時針」；凹面由多個凸面組成（共面的兩片互不施影，見 D23）。`normal`、`offset` 任意，但**沒有 bounds 的受影面只能是 `receivers[0]` 且必須是地面** z = 0（地平線、§2.3 的地面裁切、光線投射對照組與消隱的「地面遮住下方一切」都假設唯一的無界面是地面）；有無界地面時 bounds 不得在地面以下。受影面**只有正側受影**，驗證不翻轉法線；光源在負側時回報 `RECEIVER_UNLIT`。`receivers[0]` 是**預設受影面**：沿用 v1 的短名稱與 `construction` 的平面鍵；其他面在名稱後加 `.<receiver id>`（`crate.v0.shadow.lamp.wall`、`crate.v0.foot.wall`、`F.lamp.wall`、`crate.s0.lamp.wall`）。受影面 id 不可含 `.`，且不得與物件 id 重複（受影面頂點 `wall.b0` 與物件頂點共用命名空間）；彙整另加：也不得與光源 id 重複（D69）。邊泛函 `ψ_k = (m_k, −m_k·b_k)` 的 `m_k` 取**單位**向內法線，所以 `ψ_k·X` 對有限點是「帶符號距離 × w」、對方向是無因次量，§2.8 的 `tol` / `tol_dir` 才能照原來的因次使用。
- **理由**：凸多邊形的邊泛函可以直接用 §2.2 的齊次 Sutherland–Hodgman 裁切，對有界與無界影子都是閉式、確定性的（加上 D22 的錨點規則才精確）；自動翻法線會讓「哪一面受影」隨光源位置跳動，也和 M6 多光源衝突（一道牆可能兩面各被不同光源照到）。審查指出 F 與影子點本身與 π 的正負無關（M(−π) = −M(π)），這點正確，但 bounds 方向、w_S 的符號與迴圈方向都依賴 π 的方向，因此翻轉方案列為待決問題。

## D22 有界面的影子裁切：帶狀容差、方向嚴格、**錨點規則**讓 ≥ 180° 的無窮遠弧也精確（合約 §5.1.3.3）

- **問題**：審查找到反例：U 形稜柱、燈在凹口內（現有的凹多邊形案例）放到有界地板上，影子多邊形的無窮遠弧跨 270°；或半平面影子的方向頂點剛好平行板邊。純齊次 Sutherland–Hodgman 對板的邊裁切時，弧離開又回到半平面的兩個交點是**相反**的方向 ±m⊥，兩者的齊次內插經過零向量（被丟掉），後面的裁切永遠產生不出板的角，結果是**空集合**，而真正答案是整塊板（已用程式重現）。
- **決定**：每裁完一條邊，若輸出中有兩個相鄰頂點都是落在該裁切線上的方向頂點且方向相反，就在兩者之間插入該邊的有限端點 b_k（它本來就在裁切線上）：路徑「D_a → b_k → D_b」正是整條裁切線、半平面在左側，後續裁切自然產生板角；凸施影者的影子方向錐 < 180°，永遠不會觸發。容差：有限頂點以 `ψ_k·X ≥ −tol·|w|`（帶符號距離 ≥ −tol）保留，**方向頂點嚴格 ≥ 0**；帶內的保留頂點就是自己的交點、不再插入交點（和 `clip_loop_to_plane` 相同），所以剛好落在板邊上的轉折點、方塊跨牆的切面頂點不會多出一個重複的 `s<k>` 點（Python 與 TypeScript 的名稱與串列長度必須一致）。裁完後合併射影相等的相鄰頂點、丟掉 w ≤ 0 的頂點（在 §5.1.1 的轉角下限下不會發生）、面積 ≤ tol·周長的薄片視為空。所有交點與錨點都帶來源 `("bounds", k, …)`，命名為 `<obj>.s<k>.<light>.<r>`。
- **驗證**：270° 與半平面兩個反例裁切後都得到整塊板（面積 15）；有界方塊、< 180° 楔形、整個在板外的多邊形也各有單元測試。審查另一個說法「帶狀容差會讓幾乎平行板邊的方向頂點存活到最後」不成立：有界凸多邊形的向內法線正向張滿整個平面，一個方向不可能對每條邊都 ≥ −ε（除非轉角正弦小到 ε 量級，已被 §5.1.1 的 1e-9 下限排除）。

## D23 轉折影不靠裁切得到：每個施影者對每個受影面各算一次，受影面也是施影者（合約 §5.1.3）

- **規格**：§9「影子多邊形逐面計算再裁切；交線處自然轉折」；§10 M4 驗收「牆加地面案例轉折位置手算比對」。
- **問題**：地面影子延伸到牆後的部分該不該裁掉？用牆**平面**的半空間裁切會把牆板旁邊的真實影子一起刪掉（快速折衷之一，拒絕）；用牆板的影子做多邊形相減需要一般多邊形布林運算。
- **決定**：施影者先被切到受影面的正側（物件用每個（物件, 受影面）各算一次的 `obj["clipped"][rid]`，平面板用 `clip_loop_to_plane`；對地面就是 §2.3 的裁切與警告，對有界面則**靜默**），投影後只裁到該面的 bounds，**不被其他受影面裁切或相減**。有界受影面是不透光的板：對其他每一面都施影（`object` 欄位填受影面 id，頂點命名 `wall.b<k>`），也是消隱的遮擋物；**與受影面共面的板不對它施影**（否則兩片共面拼成的凹面會互相整片塗黑，或產生寬度 1e-17 的薄片，頂點數隨捨入變動）。轉折自然出現：頂點 P 的影子 `M_r P` 落在另一面 π_{r'} 上，若且唯若光線 LP 穿過兩面的交線，此時 `M_{r'} P` 是同一點；所以牆影子的底邊裁切點與地面影子跨過牆基線的交點逐點相同。地面影子延伸到牆後的部分：光線穿過板的地方落在板自己的地面影子內（nonzero 聯集仍正確，和今天兩個物件影子重疊一樣），開啟消隱時又被板擋住；光線越過矮牆的地方則是**真實的影子**，照畫。兩種情況下逐施影者的輪廓線都可能穿過另一個施影者的區域內部，輪廓合併留待日後（M6 的疊影規則也不合併輪廓，只畫各光源區域與本影）。有界面的影子裁完一定有界：`unbounded` 恆為 false，也不發 `VERTEX_NOT_BELOW_LIGHT`（頂點比燈離牆更遠是常態）。影子落在板外不是退化，沒有警告。`shadows[]` 的輸出順序是受影面 → 光源 → 施影者（物件後接其他板），多光源文件也沿用這個順序（D69）。
- **驗證**：`wall_and_ground` 手算：燈 (0,2,3)、方塊 [-0.5,0.5]×[4,5]×[0,1]、牆 y = 6，轉折點正是 (±3/4, 6, 0)，牆上頂點 (±2/3, 6, 1/3)，牆自己的地面影子頂點 (±3,6,0)、(±18,26,0)，畫面座標已用相機矩陣驗算。

## D24 非地面受影面的「逆時針」改在受影面座標系算，但地面保留 v2 的原始算式（合約 §5.1.2、§5.1.4）

- **問題**：`shadow_loop`、`curved._ground_section`、`_ground_chain`、`_ground_ring`、`shadow_polygon_h` 共五處直接用 `[:2]`、`atan2(d[1], d[0])`、`(cos θ, sin θ, 0, 0)`，都假設受影面是地面；`_direction_vertex` 的最後退路 `(1,0,0,0)` 不在牆面上，`_light_foot_from_matrix` 在 offset ≠ 0 時回傳 None，「邊穿過光源」的退路在牆上會靜默失效。審查第一輪的設計只點名其中一處。
- **決定**：受影面座標系 `receiver_frame(n)`：`e1 = normalize(z × n)`、`e2 = n × e1`（n 平行 z 時 `e1 = x`），所有上述位置在非地面受影面上改用 `((v·e1), (v·e2))`、`cos θ·e1 + sin θ·e2`；光源垂足 F_r 由光源紀錄明確傳入 `shadow_loop`，方向退路改為 `(e1, 0)`。**地面（frame 為 None）保留一字不改的 v2 算式**：三項內積可能翻轉零的符號，進而讓 `atan2` 差 2π、無窮遠弧的頂點在最後幾位不同，IEEE 不保證位元相同，所以不靠「乘 1.0 與 0.0」的說法，直接不動地面路徑；`_plane_basis` 也不替換。34 個 v2 案例的 SVG 位元相同測試是這項主張的閘門。另加一個單元測試：圓柱靠牆的場景旋轉成牆變地面，多邊形必須在 1e-9 m 內相同。

## D25 有界受影面的警告：只新增 `RECEIVER_UNLIT`，地面四個代碼只對無界面發，地面對光不透光（合約 §5.1.9、§5.0.5）

- **規格**：§5.8 退化回傳結構化警告；§2.9 的代碼表是封閉清單。
- **決定**：封閉清單只加一個代碼 `RECEIVER_UNLIT`（ids `[light, receiver]`）：有界面的光源在負側、平行光與面平行或在負側三種情況，加上**地面發 `LIGHT_BELOW_RECEIVER` 時所有板都發**（地面是不透光的：燈在地板下面不該從下面照亮牆；`DIRECTIONAL_HORIZONTAL` 不傳播，水平的太陽照得到牆）。它是清單裡**唯一刻意的資訊性代碼**：牆被從背面照不是退化，但法線反了是最可能的使用者錯誤，光看 `receivers[].lit` 容易漏掉。`LIGHT_BELOW_RECEIVER`、`DIRECTIONAL_HORIZONTAL`、`VERTEX_NOT_BELOW_LIGHT`、`OBJECT_BELOW_RECEIVER` 只對無界地面發（v2 案例的 (code, ids) 集合不變）；`SHADOW_VP_AT_INFINITY` 對預設面 ids 為 `[light]`、對其他面為 `[light, receiver]`（退化就要警告，ids 文法本來就不限於光源）。平行光與板平行時 `F.<light>.<r>` 與 `per_receiver` 的 `shadow_vp` 照樣回報，和地面的 `DIRECTIONAL_HORIZONTAL` 一致。沒有「影子落在板外」「物件在牆後」「板與相機共面」「共面施影者」的代碼，因為都不是退化。加上 M5 的四個 `MESH_*`，封閉清單從 13 個變成 18 個（合約 §5.0.5）。

## D26 取樣式消隱：對象、精確遮擋物、第一個交點判定、固定取樣與二分、預設關閉（合約 §5.1.6）

- **規格**：§9「每條邊與影子輪廓預留 visibility 欄位（可見、隱藏、分段）；M4 以取樣法填入」；§11.1「精確向量 HLR 是最難的一段，畫圖用途取樣即可」；§8 效能目標以關閉為準。
- **決定**：對象是物件邊（含背面邊）、受影面邊界邊、曲面輪廓母線與端面圓錐曲線、明暗交界線、影子輪廓（多邊形中落在原始輪廓邊上的邊，與精確圓錐曲線）；近平面或畫布矩形裁切產生的邊、兩端都是方向的邊（地平線段）是裁切產物，不是對象；作圖線、地平線、消失點、標籤是疊圖，永不消隱；填色區域（含 M6 的本影）不消隱。遮擋物是所有物件的**精確**實體（逐基元光線測試；稜柱逐側面四邊形測試，凹稜柱也正確；其他任何種類——含 M5 的 mesh——用通用封閉網格遮擋物：逐面平面交點加面內點包含，**永不拋例外**；彙整決定網格物件的遮擋面取 M5 紀錄的 `triangles`（焊接後的原始三角面），沒有該鍵的種類才用 `obj["mesh"]` 的面，D69）、有界受影面當不透光凸板、無界地面當不透光平面。判定：從相機到點 X 的射線**第一個**邊界交點 t 落在 (1e-5, 1 − 1e-5) 內即隱藏（`first_hit` 回傳第一個交點；自己物體的正面點 t = 1 不算；背面邊被自己擋住；凹口內的點沒穿過臂就可見；相機在實體內時一切隱藏）。取樣：直線以畫面比例 s 取樣，長度 `ℓ = sqrt(du² + dv²)`，`N = min(4096, max(8, ceil(ℓ/1 mm − 1e-9)))` 個中點樣本，4D 參數 `t = s·ã₃ / ((1 − s)·b̃₃ + s·ã₃)`，端點允許 w = 0（消失點落在外擴畫布內的方向頂點，已在 `degenerate_vertex_above_point_light` 重現），中點處 w > 0；畫出的 4D 端點由 `drawn_segment_4d` 從 A 段的世界端點重算（近平面裁切，再用 `P·X` 上的四個矩形泛函裁切，與 2D 路徑同樣的浮點數、同樣的內插參數；與畫出的端點相差只有一次 `P·X` 的捨入）。圓錐曲線改以**每個可見區間折線的累積長度**為參數（θ 在透視橢圓與雙曲線分支上極不均勻），邊界再以分段線性對應回 θ。狀態改變處二分**固定 6 次**：取中點 m，`v(m) ≠ v(lo)` 則保留 [lo, m]，否則 [m, hi]（一次求值、無歧義）；邊界取最後區間中點，容差 `max(1/64, ℓ/262144)` mm（ℓ ≤ 4096 mm 時 ≤ 0.016 mm，A0 外擴對角線約 2.2 m 也涵蓋）。畫面矩形剔除只在遮擋物所有極值點都在近平面前方時使用，且不得改變結果（有比對測試）。消隱在 **C 段**執行（`compose` 建好可畫圖形後呼叫 `hidden.classify_document`），因為圓錐曲線的折線在 C 段才取樣；§2.6 的取樣規則記為第三個使用處 (c)；不寫回 A、B，所有指派的串列都是新物件（`edge_templates` 共用，不得 extend）。`output.hidden_lines` 預設 **false**：§9 只說 M4「填入」欄位，§8 的目標與 CI 閘門以關閉為準，關閉時每個 v2 場景的 SVG 位元相同；開啟的成本由 `bench.py --hidden-lines` 量測並記錄（軟目標 < 5 s），關閉時 M4 前後的完整渲染時間與 JSON 大小也記錄。不接受：依時間預算或亂數調整取樣（破壞確定性）、把消隱資料放進 A 段（破壞相機無關）、用近似網格當遮擋物。
- **理由**：固定的取樣位置與固定的二分規則讓結果只取決於場景 JSON 與相機，TypeScript 移植可逐位重現；精確遮擋物讓結果與對照組一致。

## D27 `visibility` 的表示法、SVG 的隱藏線子圖層與 `hidden_style`（合約 §5.1.7、§5.1.8、§5.0.6）

- **決定**：文件頂層加 `hidden_lines`（實際生效的開關）；`visibility: "visible" | "hidden" | "partial"`，`runs` 只在 `partial` 時非空：直線 `{s, t, mm, visible}`，圓錐曲線 `{interval, theta, mm, visible}`（`interval` 是 `visible` 區間的索引、整數，因此列入 M7 的 `INT_KEYS`；每個區間各自從 0 到折線長度連續、交替；`visible` 本身不因開關改變）。`segment` 為 null 的圖形保持 `"visible"`。開啟消隱時圓錐曲線的 `arcs/ellipses/polylines` 只畫可見區間（部分隱藏的整圓改成弧；取樣折線在邊界處切開、不重新取樣），隱藏區間從同一條折線切成 `hidden_polylines`。影子多邊形每條畫出的邊各有一筆 `polygon_edges` 紀錄（關閉時為 `[]`，意為全部可見，避免每份文件多出數千個佔位 dict）。SVG：可見段畫在原本的群組；隱藏段集中到每層**第一個**子群組 `objects.hidden` / `form_shadow.hidden` / `cast_shadow.hidden`（再以物件或光源分組），樣式 0.15 mm、`stroke-dasharray="0.5 0.5"`；`hidden_style = "omit"` 時這些群組留空（真正的消隱）。開啟時影子路徑改為不描邊，輪廓另外依段描在 `cast_shadow.<light>.<object>.outline`。API：`render(scene, camera=None, hidden_lines=None, hidden_style=None)`（M6 再加 `umbra=True`），CLI 旗標傳給 `render` 而不改寫場景；`write_svg(doc, layers=None, hidden_style="dashed")`。標籤規則：名稱任一段是 `shadow` 或 `foot` 就不標（`crate.v0.foot.wall` 不標）；`F.<light>.<r>` 走 L/F 分支、不當物件頂端標籤。非預設受影面的作圖線畫在同樣的 `LP` / `FQ` / `PQ` 群組，不另分子群組（彙整決定）。
- **理由**：畫家在繪圖軟體裡需要一個開關關掉所有隱藏線，所以用每層一個子群組而不是散在各物件下；用參數而非座標存 runs 可讓 `segment` 數值與 v2 完全相同。

## D28 一致性測試集：鍵新增式的重新產生（在合併分支上只做一次，版本 v4）、runs 的比對容差、與 M5 的共用檔案（合約 §5.1.11、§5.1.12、§5.0.8）

- **決定**：文件頂層多了 `hidden_lines`、`receivers` 鍵，比對規則要求鍵集合完全相同，所以 34 個 v2 案例必須重新產生；但要求**只新增鍵**（新鍵填關閉時的值），不得改動任何既有數值、名稱、布林與警告。`regen_conformance.py --strip-new-keys` 在產生前驗證這一點（刪掉新鍵後對既有 expected 零不符），CHANGELOG 記錄。M4 與 M5 平行開發：兩邊各自只用 `--case` 加自己的案例，整組重新產生在合併後的主分支上**只做一次**（版本序列見 D67：這次重產是 v4）；共用檔案（scene.py、errors.py、cli.py、pipeline.py、raycast.py、測試與文件）裡 M4 只以附加區塊修改（`validate_bounds` / `validate_hidden_output` 附加、`RECEIVER_UNLIT` 附加在表尾、CLI 旗標一個區塊、pipeline 的 `build_object` / `_object_light_data` 呼叫點不動）。`runs` 的 `mm` 容差 0.05 mm，`s`/`t`/`theta` 絕對 1e-3，`visible`、`interval` 與段數完全相等；這條規則寫進兩個實作共用的 `tests/conformance/rules.json`（`runs_rule`，D54）。
- **理由**：取樣邊界在不同浮點實作間只能重現到二分區間的寬度（≤ 0.016 mm），1e-6 mm 的規則對它沒有意義；其餘幾何仍用原規則。

## D29 消隱的對照組：逐像素光線投射的深度緩衝，三值判定（合約 §5.1.11）

- **規格**：§10 M4 驗收「消隱結果與對照組深度一致」。
- **問題**：以「緩衝深度 < 樣本深度 × 0.98」判隱藏時，掠射的遮擋物（方塊正面對底邊 v1–v2 的前 1.68 mm，交點參數 0.98–1.0）在對照組裡是「不隱藏」，而取樣法正確地判為隱藏；要求 100 % 一致必然失敗。
- **決定**：`tests/reference/zbuffer.py` 與 castplane 零共用程式碼，依規格重做相機，對外擴畫布每 0.1 mm 一個像素從相機射線求最近交點深度（物件、板、地面），深度一律用相機空間 x̃₃。判定是**三值**的：`Z[px] < depth·0.98` 隱藏、`Z[px] > depth·1.02` 可見、其間**未定**（不計入百分比）。每條 run 每 0.5 mm 取樣（兩端各留 0.3 mm）與緩衝比對：全文件已判定樣本 ≥ 99 %、方塊與稜柱的邊 100 %；每個 run 邊界前後 0.15 mm 以點對點光線投射確認（≥ 98 %）。2 % 深度帶與 0.3 mm 端點邊界是對照組本身的限制（輪廓像素、掠射的遮擋物），記錄在合約裡。

## D30 網格物件的幾何一律內嵌在驗證後的場景裡；載入器只住在輸入層的展開步驟；「沒有可用的面」在驗證時就報錯（合約 §5.2、§5.2.1、§5.2.2、§5.0.2）

- **規格**：§4 說 v2 加 `mesh（path）`；§8 要求核心只依賴 numpy、載入（trimesh）為可選套件；§9 要求 TypeScript 移植核心但不含載入器，一致性測試集兩邊共用；§5.8 / 合約 §2.0 要求輸入錯誤由驗證以欄位路徑回報、退化情況只警告不拋例外。
- **問題**：若 A 段自己讀檔，核心就依賴檔案系統與載入器，TypeScript 無法從場景 JSON 重現文件。另外，若「焊接並去掉退化面之後一個面都不剩」到 A 段才拋錯，`castplane validate` 會說 OK、`castplane render` 卻以錯誤碼 2 結束，違反「驗證通過就能畫」。
- **決定**：`mesh` 物件在寫出的場景裡用 `path`（檔案）或 `data`（內嵌 `vertices` / `faces` / `smooth_groups`）至少其一；兩者都有就視為已展開（用 `data`，`path` 只供參考），沒有「兩者都給」的錯誤，`expand_scene` 才能冪等。**彙整修正**（D68）：讀檔不在 `validate_scene` 裡做，而是在驗證**之前**由 `castplane.io.expand_scene` 把 `path` 展開成 `data`（含 glTF 的 Y-up → Z-up 轉換與節點變換烘焙、M8 的 `.step` 網格化），之後 `validate_scene`、A/B/C 段與前處理只看 `data`；`validate_object` 遇到只有 `path` 的 `mesh` 回報 `objects[i].path`「必須先展開」。相對路徑以場景檔所在目錄為 `base_dir`，給 dict 時以目前工作目錄為準（與 M8 一致；原設計「dict 沒給 base_dir 就報錯」撤回）。驗證另外跑一次焊接＋退化面移除（只有 numpy、O(V+F)），沒有任何可用的面就回報 `objects[i].data.faces`（檔案來源回報 `objects[i].path`）；驗證後的 `data` 仍是原始資料。glTF 檔配 `up` 鍵是矛盾輸入，展開時回報 `objects[i].up`。一致性案例一律用 `data`，移植版不需要任何載入器。`node` 可以是名稱字串或整數索引（glTF 節點索引、OBJ 第 k 個群組名），名稱以深度優先遍歷的第一個相符者為準；匯入器在名稱空白或重複時寫索引，所以匯入器自己寫出的場景一定能再讀。
- **理由**：載入器的錯誤有欄位路徑、可選套件缺少時走 exit 3，核心仍是純函式；驗證通過的場景保證能渲染；`castplane.load_scene` 保持純函式，M8 的 `step` 與 M5 的 `path` 走同一條展開路徑。

## D31 軸轉換是精確的分量置換，不是三角函數旋轉（合約 §5.2.1、§5.2.8）

- **問題**：`Rx(+90°)` 用 `cos` / `sin` 算，`(1, 0, 2)` 會變成 `(1, −2, 1.2e−16)`；每個轉換過的頂點、光源與相機位置都帶 1e−16 雜訊，Y-up 的方塊就不再與參數化方塊**完全相等**（驗收要求逐位元相同），匯入器也會寫出 `1.2246e−16` 這種座標。
- **決定**：`A = [[1,0,0],[0,0,−1],[0,1,0]]`（整數），`(x, y, z) ↦ (x, −z, y)` 以分量交換與變號實作，`Aᵀ` 同理；`up: "y"` 與 glTF 載入器都用這個精確映射。
- **理由**：這是唯一能讓「匯入的方塊 = 參數化方塊」精確成立的做法，Python 與 TypeScript 也必然一致。

## D32 焊接規則：格子鍵加 27 鄰格、取所有候選中輸入索引最低者、取代表點原座標、依首次出現編號（合約 §5.2.3 第 2 步）

- **規格**：§9「焊接頂點」，未定容差與合併後的座標。
- **決定**：格子大小 = `weld_tolerance`（預設 1e-6 m，`scale` 之後），鍵為 `floor(x/τ + 0.5)`；依輸入順序逐頂點看 27 個鄰格裡**所有**最大範數距離 ≤ τ 的代表點，取輸入索引最低者（檢查鄰格的順序無關緊要），沒有就自己成為代表。合併後的座標是**代表點自己的座標**，不取平均；代表點依首次出現編號，名稱 `<obj>.v<k>`；沒有任何面用到的頂點移除。參考實作是 O(27·n) 的 Python 迴圈（五萬頂點約 1 秒）；向量化的快速路徑只有在測試證明結果完全相同時才允許。`scale` 在焊接之前套用，毫米檔案要給 `scale: 0.001`。
- **理由**：平均值會讓「匯入的方塊」與參數化方塊差幾個 ulp；`floor(x+0.5)` 在 Python 與 JavaScript 行為一致（`round` 不是）；首次出現編號可移植、確定。

## D33 退化面：連續重複先折疊、頂點必須兩兩不同、Newell 法線太短就丟（合約 §5.2.3 第 3 步）

- **問題**：`[a,b,c,b]` 這種面有三個不同頂點、法線不為零，卻在同一個面裡把邊 (b,c) 走兩次（方向相反），流形檢查會把它當成「兩個面共用」而誤判為流形。
- **決定**：折疊連續重複後，頂點數 < 3、頂點不兩兩相異、或 Newell 法線長度 ≤ 1e-12·scale² 的面一律丟掉並回報 `MESH_DEGENERATE_FACES`；流形檢查以**不同的面索引**計數。
- **理由**：鄰接表只有在每條邊屬於兩個不同的面時才有意義。

## D34 方向修正：流形但繞向不一致時先傳播、再依有號體積與巢狀深度決定內外（合約 §5.2.3 第 5 步）

- **決定**：每條邊恰有兩個不同的面才算流形（邊界邊即非流形）；兩面同向走同一邊時，從每個連通分量最低索引的面做 BFS 傳播翻轉（翻轉保留第一個頂點），衝突（莫比烏斯、克萊因瓶式的連接）視為非流形且訊息寫明「inconsistent winding」。再對每個分量算有號體積；分量 k 的巢狀深度 = 以 k 的最低索引頂點對**其他**分量算廣義纏繞數、`|w| > 0.75` 的分量個數；深度為偶數要朝外（體積 > 0），奇數要朝內（空腔殼保留朝內法線）；原始體積符號不對就整個分量翻轉。有翻轉即回報 `MESH_WINDING_FIXED`；體積在 1e-12·scale³ 內視為零、不翻不警告也不參與巢狀。步驟順序定為焊接 → 退化面 → 流形／方向 → 共面合併 → 二面角分類（規格 §9 的順序是合併 → 二面角 → 流形），因為合併需要一致的外向繞向。
- **理由**：匯入檔的繞向常不一致或整體朝內；只看體積符號會把中空物件的內殼翻成朝外，讓空腔裡的光源被判成「在物件內」（w = 2）並產生多餘的光輪廓迴圈。

## D35 共面合併：以種子順序做 BFS 區域生長、起點取種子面第一個在邊界上的頂點、孤兒頂點保留（合約 §5.2.3 第 6 步）

- **規格**：§9「合併共面三角形」。
- **問題**：並查集依邊的處理順序決定分割，同一個規則在不同順序下會給不同結果，無法手算也難移植；「從種子面的第一個頂點開始」在中心扇形三角化的端蓋上無法套用（中心點不在邊界）。
- **決定**：面依索引順序當種子，BFS（FIFO、鄰居依共用邊索引遞增）生長；鄰面加入的條件是尚未指派、與**種子**法線夾角 ≤ 1e-3 rad、且與抵達它的面夾角 ≤ 1e-3 rad。區域邊界不是單一簡單迴圈（有洞、夾點）時整個區域不合併。合併後的多邊形從種子面循環中第一個落在邊界上的頂點開始、沿邊界本身的方向走；種子沒有任何頂點在邊界上時從索引最低的邊界頂點開始。合併後沒有任何面用到的頂點（端蓋中心）**保留**：名稱、`points` 不變、`triangles` 仍指向它，只是沒有邊。
- **理由**：三角化後的方塊合併回與 `box_mesh` 完全相同的六個四邊形（同順序、同起點）；彎曲條帶的分割可以手算（步距 1.5e-4 rad 時為 {0..6}、{7..13}、{14..19}）；1e-3 rad 容得下 float32 檔案的法線誤差。

## D36 平滑邊與相機輪廓邊：平滑邊只在成為相機輪廓時才畫；平滑群組不同即為特徵邊（合約 §5.2.3 第 7 步、§5.2.4）

- **規格**：§9「以二面角分特徵邊與平滑邊」，§6.1「物件所有邊都畫」。
- **決定**：邊為平滑 ⇔ 兩面同屬同一個非零 OBJ 平滑群組，或兩面都無群組且 `n_a·n_b ≥ cos(smooth_angle_deg) − 1e-9`（預設 30°）；群組不同、或一邊有群組一邊沒有，一律是特徵邊。A 段決定（與相機無關）。物件圖層畫一條邊 ⇔ 非平滑或為**相機輪廓邊**（兩面對 (C,1) 的 `lit` 不同，B 段決定）。不畫的平滑邊 `segment` 為 null，`visibility` 維持樣板值（M4 的取樣器只處理畫出來的線段）。只有 `mesh` 物件的 `edges[]` 多兩個鍵 `smooth`、`camera_silhouette`，基元的邊不加鍵，所以既有 expected 檔不因 M5 改變。
- **理由**：匯入的曲面網格畫出全部三角邊會是一團黑；建模者設不同的 `s` 群組就是要硬邊；1e-9 的帶寬避免共面但未合併的區域因最後一個 ulp 在平滑／特徵之間跳動（合約 §2.8 禁止等號判定）。

## D37 非流形退路：逐面投影、單一路徑 nonzero 填色、保留垂足但不畫作圖線、絕不做地面切割（合約 §5.2.5）

- **規格**：§9、§11.3「非流形退路為逐面投影取聯集」。
- **問題**：`clip_mesh_to_plane` 會把開放網格的開口邊緣接成端蓋面，一個埋入地面的開口方塊會被當成封閉實體投影（已重現）；`compose` 把所有紀錄的 `foot_names` 與 `keep` 串接後成對轉換，沒有垂足的紀錄會讓後面所有紀錄的點名錯位。
- **決定**：退路物件永遠 `ground_mesh = None`，對每個受影面 `clipped[r] = None`（仍回報 `OBJECT_BELOW_RECEIVER`，每個面的迴圈由 `shadow_loop` 自己裁切，有界受影面再逐迴圈做 D22 的 bounds 裁切——彙整決定）；不做光源在內測試、不走 `silhouette_loops`。每個面（背光面先反轉繞向，讓受光側在左）各自走 `shadow_loop`，每面一個迴圈，面積測試只對有界迴圈做，交點以原始邊 `(min, max)` 為鍵、一點一名；全部寫進同一個 `<path>` 以 nonzero 填色取聯集。所有被面用到的頂點都有 `.shadow` 與 `.foot` 點，但 `ray_vertices` 全為 False：沒有作圖線、自我驗證與線段。`edge_faces` 取該邊所屬的最低與最高索引面（邊界邊兩者相同），`back` 與 `silhouette` 依此近似計算；回報 `MESH_NON_MANIFOLD`。落在受影面上的面會投影成自己的腳印，而光線投射對照組忽略 t ≤ 1e-9 的命中，驗收案例因此用「沒有底面」的方塊。
- **理由**：沒有鄰接就沒有光輪廓；逐面聯集對任何面集合都正確（與 §7.3「射線碰到任一面」語意相同）；保留垂足不需要改 `compose`，只靠 `ray_vertices` 遮罩就能拿掉作圖線。

## D38 網格的作圖線只給特徵輪廓頂點、每物件每光源最多 64 條；在實際使用的迴圈網格上計算（合約 §5.2.4）

- **問題**：部分埋入地面的網格在 `_shadow_record` 裡會換成切割後的網格重新算輪廓頂點，若遮罩在 `_object_light_data` 用整個網格算就會對不上長度。
- **決定**：候選頂點 = 至少接一條**特徵**光輪廓邊的原始輪廓頂點，在實際使用的（可能已切割的）迴圈網格上判定：切割後的邊繼承它所屬原始邊的平滑旗標，切面上的邊是特徵邊，交點頂點永遠不是候選。依迴圈順序取前 64 個，超過回報 `MESH_RAYS_CAPPED`；輸出順序維持既有的頂點索引遞增順序（遮罩只做選取）。所有輪廓頂點仍有 `.shadow` / `.foot` 點。方塊網格因此得到與參數化方塊相同順序的作圖線。
- **理由**：平滑輪廓上的上千個頂點各畫三條線毫無作畫價值；輸出順序不變才能讓方塊案例與解析案例逐字相同。

## D39 glTF 的軸、節點、相機與光源映射（合約 §5.2.8）

- **決定**：`matrix` 為行主序 16 個浮點數、`rotation` 為單位四元數 `[x, y, z, w]`、`local = T·R·S`、`world = parent·local`，依場景根節點、子節點陣列順序做深度優先遍歷（這個順序也定義「第一個同名節點」）；頂點先乘世界矩陣（行列式為負時反轉面）再做精確軸映射。相機 `yfov` → `focal_length_mm = 12 / tan(yfov/2)`、片幅高 24 mm、寬 `24·aspectRatio`（預設 1.5）、畫布為片幅 ×10；朝向取 R·(0,0,−1)，R 為正規化後的旋轉部分，滾轉由 up 向量對 castplane 未滾轉的 (right₀, up₀) 以 `atan2(−up·right₀, up·up₀)` 求得。點光取位置；平行光方向 = 正規化的 `A·(R·(0,0,+1))`；聚光燈退化為點光並記 `IMPORT_SPOT_AS_POINT`；多於一台相機取遍歷順序第一個、其餘記 `IMPORT_CAMERA_DROPPED`；**光源全部輸出**（彙整修正：M6 已在同一份合約裡解除「只能一盞光」，`IMPORT_LIGHT_DROPPED` 撤銷；`--light NAME` 只保留一盞；輸出 ≥ 2 盞時 id 為 `umbra` / `core` 者加後綴 `_light`）；沒有相機或光源時給確定的預設值並記錄。extras 基元參數以 castplane 局部慣例書寫，節點只能有**均勻且為正**的縮放（乘進參數），非均勻、非正縮放或鏡像節點（行列式 < 0）回報 `nodes[k].scale` / `nodes[k].matrix` 錯誤。網格節點以名稱引用，名稱空白或重複時改以索引引用。
- **理由**：這是 glTF 規範唯一無歧義的對應；鏡像節點無法用正常旋轉的歐拉角表示，與其寫出垃圾角度不如拒絕；匯入備註不是幾何退化，不進 §2.9 的封閉警告清單，而是寫到場景的 `meta` 區塊並印到 stderr（與 M8 的備註同一套機制，D68）。

## D40 網格大小上限、效能、與 M4 的合併順序（合約 §5.2.1、§5.2.7、§5.2.9）

- **決定**：載入後面數與頂點數各 ≤ 50 000，超過為輸入錯誤，不是警告。`triangles` 只加在 mesh 紀錄上（基元不加，M4 需要時自己用向量化的 `mesh.triangulate_faces` 加），關閉功能時基準路徑只多一個逐邊布林比較，差額記在 `benchmarks/README.md`；另加 `bench.py --scene mesh10k` 記錄一萬三角形網格的實測，不設閘門。M4 先合併並重產整組一致性案例（v4），M5 之後 rebase 再只用 `--case` 加三個網格案例（v5）；合約章節以里程碑順序編號（M4 = §5.1、M5 = §5.2），警告表寫「+4 個代碼」、總數 18。
- **理由**：§6.2 文件每條邊一個 dict，五萬面已是互動用途的上限；上限明確比靜默變慢好；兩個工作樹不互相覆蓋版本號與 expected 檔。

## D41 哪些「快捷做法」可接受（合約 §5.2.10）

- **可接受**：glTF 只處理三角形（條帶與扇形展開）；trimesh 只當 STL/PLY 的讀檔器（`process=False`）；OBJ 多邊形以扇形三角化供射線測試；作圖線上限 64；巢狀深度每個分量只算一次纏繞數。
- **不可接受**：用 trimesh 的 `merge_vertices` / `fix_normals` 當前處理（版本相依的順序破壞位元確定性、TypeScript 無法重現）；焊接取平均座標；在 A 段用相機分類平滑邊；省略共面合併；並查集式合併（結果依邊的順序）；三角函數軸轉換；在 A 段拋「沒有可用的面」；在 `validate_scene` 裡讀檔。

## D42 多光源文件 = 單光源文件加「多光源擴充」，只在 `lights` 長度 ≥ 2 時出現（合約 §5.3.0、§5.3.5）

- **規格**：§9「v1 的資料結構與 API 現在就按後續版本的形狀設計，之後只加功能、不改介面」；§10 M6「多光源影子分組、疊影規則、SVG 子圖層」，相依 M4。
- **問題**：多光源需要每個光源各自的作圖區塊、本影、各光源的形體陰影、各光源的光輪廓邊與曲面作圖點名稱；若無條件加進文件，單光源場景的 §6.2 文件與一致性測試集全部改變，違反 §9。
- **決定**：`lights` 改為非空陣列（不設上限）。「多光源文件」定義為 `len(lights) ≥ 2`；只有多光源文件多出 `constructions`（每光源一個作圖區塊，形狀與 M4 的 `construction` 相同、含 `per_receiver`——彙整決定，D69）、`umbra`、`form_shadow_core`、`form_shadow[].light`、`edges[].silhouette_lights`（該邊對哪些光源是光輪廓邊，依場景順序；`silhouette` 本身改為「對任一光源成立」，單光源不變）與帶光源 id 的曲面作圖點名稱；`construction` 永遠等於 `constructions[lights[0].id]`（舊介面別名）。只有多光源場景才拒絕光源 id `umbra`、`core`（那是多光源 SVG 子圖層的 id；單光源場景取這些名字仍合法）；彙整另加：多光源場景的物件 id 也不得是 `core`（與光源 id 的規則對稱，讓 `form_shadow.core` 這個前綴只屬於核心群組；多光源文件裡物件群組是 `form_shadow.<light>.<obj>`，而光源 id 不可能是 `core`，所以本身不會撞名），任何場景的物件／受影面／光源 id 都不得是 `hidden`（M4 的 `*.hidden` 子群組）。單光源文件與 SVG 逐位元不變（基準是 M4 合併後的 v4 形狀，不是 v1——因為 M4 加的是無條件鍵且先合併），現有 expected 檔不動，測試集只新增四個多光源案例（v6）。
- **理由**：§9 禁止改介面；條件規則對移植版只是一個旗標。日後若重新產生測試集，也不要改成無條件鍵，理由相同。

## D43 本影在畫面空間由各光源的可畫區域相交求得，是依賴相機的可畫圖形；少於兩個有效光源時為空；逐受影面計算（合約 §5.3.1、§5.3.4、§5.3.8）

- **規格**：§9「本影為各影子交集、半影區分」，未說在哪個空間算。
- **推導**：受影面到畫面的中心投影 φ 在近平面前方是單射，所以 φ(A ∩ B) = φ(A) ∩ φ(B)；每個光源的可畫影子多邊形正是 φ(影子 ∩ 近平面前方) ∩ 外擴矩形，線段映成線段，因此畫面上各光源可畫區域的交集就是世界本影的精確影像（限於近平面前方、外擴矩形內，而外擴矩形包含畫布）。引理對每一個受影面平面各自成立；M4 的每筆影子紀錄只落在一個受影面上（轉折影是兩筆紀錄），所以本影與 M4 無縫組合。
- **決定**：`umbra[]` 每個受影面一筆；`umbra[].lights` 是**該受影面上有效**的光源（`receivers[r].lit[light]` 為真者，場景順序；對無界地面即不在 `LIGHT_BELOW_RECEIVER` / `DIRECTIONAL_HORIZONTAL` 警告裡的光源，對有界面即沒有 `RECEIVER_UNLIT` 的光源——彙整決定）；`polygons` 定義為這些光源**畫出來的區域**的交集，只在有效光源 ≥ 2 時計算，否則為 `[]`（這是決定，不是物理：一個有效光源時它的整個影子本來就是本影，子圖層已經畫了；全部失效時物理本影是整個受影面，刻意不輸出）。光源在某物件內部（`LIGHT_INSIDE_OBJECT`）**不**略過：沿用 v1 保留它對其他物件的影子，本影以畫出的區域計算，因此這種場景輸出的本影是物理本影的子集；這樣本影與子圖層畫的東西永不矛盾，測試以文字寫明這是取捨。本影在 B 段由 `shadows[].polygons`、`umbra[].lights` 與 `canvas_mm` 純函式算出（移植版只憑 JSON 重算，逐位元比對）。本影沒有世界座標、沒有具名點；各光源的影子紀錄仍與相機無關。測試把碎片映回受影面用該面的單應 `H_r = P·E_r`（`E_r = [e1 e2 o_r; 0 0 1]`，地面即 `P[:, (0,1,3)]`）。曲面影子用取樣後的可畫多邊形，不算圓錐曲線交點。半影不另外輸出多邊形：規格 §9「半影區分」在畫面上由各光源子圖層的淡色與其上的本影區分，文件使用者可用各光源區域減去本影碎片自行求得（不需多邊形布林運算）。`project_scene(..., umbra=False)` 讓互動介面略過計算（`polygons` 為 `null`，一致性測試永遠計算）。
- **否決**：在 A 段算世界本影（無界影子要做有向射影布林運算）；柵格化或 SVG 混色模式（不精確、不在文件裡）；有效光源只有一個時也把它的區域切成碎片輸出（文件重複唯一的影子，SVG 不會多畫任何東西）。

## D44 一個掃描線核心：nonzero 分解、吸附事件、區間合併、逐光源繞數相交（合約 §5.3.4、§5.3.7）

- **問題**：凹稜柱的單一影子迴圈可能自交，多個自影迴圈會重疊或有孔洞，耳切法不成立。審查又證明：梯形逐對凸裁切在基準場景每光源有 61 226 個原始梯形，先做每光源聯集更膨脹到約 15 萬片、16 秒，配對矩陣 21 GB；頂點落在另一光源邊上時裁切的起點隨建置環境的最後一位捨入而轉動，索引式比對會失敗。
- **決定**：只用一個核心 `scan_pieces`：(1) 所有頂點的 v 排序後以 `tol_mm = 1e-9·D`（D 為外擴矩形長邊）貪婪合併，頂點的 v **吸附**到合併後的事件值（沒有頂點落在水平帶內部，幾乎水平的邊變成恰好水平並丟棄）；(2) 非相鄰邊對的交點（u、v 範圍重疊的候選對以掃掠列舉，公式寫在合約）加入事件，距頂點事件 `tol_mm` 內的交點丟棄；(3) 每個水平帶以中點判定有效邊，`x(y)` 在端點取精確值，依 `(x_mid, 邊索引)` 排序，**每個光源各一個繞數**，所有光源繞數皆非零的連續區間合併成一片（內部邊不當邊界）；(4) 兩端分別取 min/max 夾住（交點被合併進帶邊界時不會出現蝴蝶結，誤差面積 ≤ tol_area/2）；(5) 相鄰水平帶中左右邊界「線 id」相同的片段縱向合併（同一條線的子段共用線 id，所以輸出複雜度是區域本身而非帶格）；(6) 兩端寬度 ≤ tol_mm 的收成一點，面積 ≤ `tol_area = 1e-9·D²` 的丟棄，每片轉到**標準起點**（v 最小者，tol 內取 u 最小）。每筆影子紀錄先各自分解（nonzero，一組繞數），再把所有有效光源的碎片（皆逆時針、繞數 +1，不會互相抵消）一次掃描相交，輸出互不重疊的凸片，集合與光源順序無關。
- **驗證**：正方形、重疊、孔洞、蝴蝶結、C 形自交迴圈（4 片、面積 19.0）、薄片與吸附案例；手算案例（兩對稱點光、單位方塊：本影六邊形 (±0.5, ±0.5)、(0, ±2/3)，地面面積 7/6，畫面三片，座標逐位元等於手算值）在四組剛體變換下索引式穩定到 7e-14 mm；基準場景兩光源 3 637 片／光源、本影 3 514 片，與柵格 AND 的 IoU = 1.0；三光源凹稜柱 25 片。

## D45 形體陰影分光源，另加全光源背光的「核心」；平面板視為單面多面體（合約 §5.3.3、§5.3.5、§5.3.6）

- **決定**：面「背光」是相對某光源的判定；只被部分光源背光的面被其他光源照亮，不該畫成全黑。多光源文件的 `form_shadow[]` 每筆帶 `light`（光源優先、再物件順序；曲面物件的明暗交界線也分光源），另有 `form_shadow_core`（被所有光源背光的面，平行視為背光，光源在實體內視為全背光；曲面物件沒有核心）。M4 的平面板（相機看到的那一面不受光時的 `form_shadow` 項目；這類項目的**存在與否**取決於相機，在 B 段決定，合約 §5.0.3 因此把板的 `form_shadow` / `form_shadow_core` 項目列為相機相依，物件的項目仍與相機無關）在多光源下當作單面多面體套同一套規則（彙整決定）。SVG：`form_shadow.<light>`（透明度 0.18/N_act）只畫該光源背光**且不在核心**的面，`form_shadow.core` 以 0.18 畫核心面一次，所以核心就是 v1 的色調、半背光面是 0.09（N_act = 2）。

## D46 SVG 疊影樣式、以有效光源數為分母、子圖層 id 與順序（合約 §5.3.6、§5.0.6）

- **決定**：N_act = `umbra[].lights` 聯集的光源數（至少 1）。`cast_shadow.<light>` 各帶 `fill-opacity = 0.3/N_act`，其上 `cast_shadow.umbra`（`fill="#000" fill-opacity="0.3" stroke="none"`）以每個受影面一個 `<path>` 放入所有本影碎片（碎片互不重疊、不描邊：每段本影邊界都已被某光源輪廓線描過）。N_act = 2 的合成：本影 0.494、單物件半影 0.15、同光源兩物件重疊 0.2775（v1 的重疊行為）；一個失效光源時唯一的影子仍是 0.3、本影路徑為空，畫面等於單光源。`construction.<light>` 分組，標記與 LP/FQ/PQ 顏色不變。光源子圖層依 id 字元順序。與 M4 的隱藏線子群組合併後，每層內的順序統一為：`*.hidden`（有消隱時，最先）→ 各光源群組 → `cast_shadow.umbra` / `form_shadow.core`（合約 §5.0.6）。否決群組 `opacity`（會連輪廓線一起變淡、破壞單光源一致）。單光源 SVG 逐位元不變，測試以群組 id 清單與 M5 合併後產生的黃金檔驗證，不把整個 SVG 寫死在測試裡。

## D47 曲面物件依光源而異的作圖點名稱放在基本名最後，組合規則不變（合約 §5.3.2、§5.0.4）

- **問題**：球的 `sil.<k>`、圓柱與圓錐的 `g<k>.base/top` 隨光源不同，兩個光源會撞名（實測第二個光源覆蓋第一個的 `ball.sil.0`）；程式有五處以字串拼接組名（`stage_a_object`、`_loop_entries`、`_terminator_segment_names`、`_project_shadows`、SVG 標籤過濾）。
- **決定**：多光源文件中依光源而異的**基本名**加光源 id：`<obj>.sil.<k>.<light>`、`<obj>.g<k>.base.<light>`、`<obj>.g<k>.top.<light>`；影子與垂足沿用 §3.1 唯一規則：`<基本名>.shadow.<light>[.<r>]`（光源 id 刻意出現兩次）、`<基本名>.foot[.<r>]`。`c`、`apex`、`v<k>`、`v<k>.foot`、`og<k>` 共用不變。五處組名都改成從紀錄的名稱清單取基本名再加字尾，標籤規則不動；測試對每個點名做文法往返（由右往左依已知的受影面 id 與光源 id 解析，所以受影面 id 不得與光源 id 重複，D69）。不保留 `shadow`、`foot` 當光源 id（v1 允許，名稱由右往左對照已知 id 解析不會歧義）。

## D48 多光源不新增警告、ids 不變；效能只量測不設目標（合約 §5.3.8、§5.3.9）

- **決定**：§2.9 封閉代碼表不因 M6 改變；`[object]` 類警告跨光源去重，`[light]` 類逐光源。兩個光源同位置、全部光源失效、光源只在某物件內，都不是退化。§8 的目標與閘門仍以單光源基準場景量測（N = 1 程式路徑不變，重新量測記錄）；兩、三個光源的完整渲染、只換相機（含與不含本影）與本影單獨時間列為資訊列（原型實測兩光源本影 2.3 s，其中 numpy 核心約 0.3 s，其餘是原型的逐片 Python 迴圈，實作必須向量化），另加 2 000 邊迴圈的分解時間（M5 網格情況）；不設目標，M7 拖曳時以 `umbra=False` 略過。

## D49 TypeScript 移植沿用 Python 的函式名稱（snake_case）（合約 §5.4.2）

- **規格**：§8「函式名稱沿用第 5 節符號（lit、silhouette_edges、shadow_matrix、foot、project）」；§9 要求兩個實作共用一致性測試集。
- **問題**：TypeScript 慣例是 camelCase；若改名，兩邊程式碼無法逐函式對照，移植與審查都要多一層對應表。
- **決定**：凡 Python 有同名函式者，TS 匯出名稱完全相同（`shadow_matrix`、`light_vector`、`shadow_geometry`、`project_scene`、`compose`、`render`、`load_scene`、`write_svg`、`dumps`、`row_max_abs`、`shadow_w`…）；Python 只有批次（複數）形式的函式（`covering_segments`、`extended_segments`、`clip_segments_uv`、`clip_segments_rect_h`）在 TS 保留複數名、輸入輸出都是串列、逐列計算；只存在於移植版的名稱（`load_scene_text`、`pymod`、`pyimod`、`py_round`、`py_repr`、`cmp_code_points`、`jacobi_eigenvalues_3`、`construction_block`、`fmt`）在合約表格的「port-only」欄明列。型別用 PascalCase；模組檔名與 `castplane/*.py` 一一對應（第二階段含 `hidden`、`meshprep`、`umbra`、`multilight`）。
- **理由**：規格的「公式與程式碼一一對應」在兩個實作之間同樣成立，grep 一個名字就能同時找到兩邊；改名或新名都要明文登記，不能默默發生。

## D50 工具鏈：node:test、tsc、兩份 tsconfig、零執行期相依、版本釘死（合約 §5.4.1）

- **規格**：§8「核心只依賴 numpy」的對應物是 TS 核心零執行期相依；§9 要求網頁 UI 用 three.js。
- **決定**：`ts/` 以 `tsc` 建置（ESM、宣告檔、source map），測試用 node 內建的 `node:test`，不用 vitest；`web/` 用 vite 8.3.3 + three 0.186.1（@types/three 0.186.0），TypeScript 釘在 6.0.2，node ≥ 20.19；版本一律精確釘死（含 `@types/node`，不用 `^`）並提交 `package-lock.json`。`ts/tsconfig.json` 只編 `src/`、`types: []`、`lib: ["ES2022"]`——這就是「核心同時能跑在瀏覽器與 node」的證明：`src/` 底下任何 `node:` 匯入、`process`、`Buffer`、`performance` 都編不過（以 tsc 6.0.2 實測：TS2591／TS2304）；`ts/tsconfig.test.json` 繼承它、加 `types: ["node"]`、納入 `test/` 與 `bench/`，輸出到同一個 `build/`。
- **理由**：`node --test` 直接執行 `tsc` 的輸出，測的就是出貨的程式碼，中間沒有第二個編譯器（esbuild）可能改變浮點或模組順序；核心本來就沒有相依，加 vitest 只多 100 個套件。單一 tsconfig 不可行（審查時實測）。TypeScript 7（Go 版編譯器，2026-07 發布）砍掉部分選項、本倉庫尚未驗證，先用 CI 容器已安裝的 6.0.2，之後升級只改一行。

## D51 以純量路徑為移植語意；固定運算順序；libm 差異由容差吸收，但放大 ulp 的幾何要明文記錄（合約 §5.4.4）

- **規格**：§8「無浮點累加順序差異」、§7.5 容差 1e-6 mm；合約 §2.8 要求固定形狀運算。
- **問題**：numpy/BLAS 可能用 FMA 或不同的加總順序，V8 不會；`math.acos` 等 libm 與 V8 的 fdlibm 末位可能差 1 ulp。兩邊不可能位元相同。而且 ulp 級的差異在某些幾何會被放大：若 `w_S(θ) = A cos θ + B sin θ + C` 的零點是重根（圓柱頂緣剛好切到光源高度），零點位置對輸入的敏感度是平方根型（1e-16 → 1e-8）。
- **決定**：(1) TS 實作 Python **純量**路徑的語意（`_project_polygon`、`_project_shadow`、`stage_b_object`），批次核函式只是 Python 的效能手段，必須與純量路徑位元相同——`project_polygons` 已有測試，`stage_b_objects` 原本只有「一次批次投影」的說明、沒有相等性測試，M7 先補 `tests/test_curved.py::test_stage_b_objects_equals_per_object_loop`（34 個案例逐字相等）作為移植的前提；M4–M6 允許的向量化快速路徑（焊接、本影分塊、消隱剔除）各自也要有結果相同的測試；(2) 每個內積都按索引順序寫成明確的和，裁切插值用 Python 的公式 `(fa·B − fb·A)/(fa − fb)`；(3) 變長加總只有 Newell 法向量、鞋帶面積、地面截面中心三處（第二階段再加 M5 的有號體積與纏繞數、M6 的前綴和，都依合約寫明的順序循序累加），TS 依頂點順序循序累加；浮點鍵的穩定排序有兩處（`_ground_section`、`_ground_ring` 的角度鍵），TS 用明確比較器加索引決勝；(4) 條件數改用對稱 3×3 Jacobi 特徵值（SVD 的奇異值即 |λ|，門檻 1e8 粗到不在乎最後幾位；停止條件是非對角範數為 0、或上一輪沒有下降、或 64 輪，不依賴 denormal）；(5) Python 的浮點 `%` 以 `pymod` 精確重現 CPython 的 `float_rem`（七處，合約逐行列出，M4–M6 新增者在第二階段補列）；左運算元可能為負的整數 `%`（`pieces[(i − 1) % n]`、`qi % 4`）用 `pyimod`，否則 JS 會取出 `undefined`；`int(round(q))` 用四捨六入五成雙的 `py_round`；測試會 grep `ts/src` 強制這條規則；(6) 沒有容差帶的判定（`>= 0`）照抄，若某案例恰好落在這種邊界而兩邊結果不同，改案例不改判定——除非邊界就是案例的目的（見 D60）。
- **證據**：設計階段的探針把每個核函式的**輸入**逐元素、正負交錯地乘上 `1 ± 2^-52`（先前的探針是把齊次結果整體乘上常數，在射影意義下等於什麼都沒做，不算證據）：擾動 `P`、世界頂點、裁切輸出時 34 案例全過；擾動 `M` 或 `L` 時 33 過、唯一失敗的是 `degenerate_cylinder_cap_at_light_height` 的四個葉節點（`shadows[0].loops[0][30]`、`[31]` 與 `outline` 同兩項的 `direction[1]`，相對差 3e-9，放大器是 `curved._zero_shift` 的 `acos(c0) − acos(c1)`，|c| → 1）。其他所有葉節點對一個 ulp 的輸入變化至少有 3 倍餘裕。M4–M6 的新案例凍結前要重跑這個探針。

## D52 標準 JSON 寫出器：重現 Python 的 repr 規則與整數欄位清單；非有限數兩邊都拒絕（合約 §5.4.5）

- **規格**：§8「相同輸入產生位元相同的 JSON」；合約 §3.1 規定 `json.dumps(sort_keys=True, indent=1, ensure_ascii=False)` 加 repr 浮點數。
- **問題**：JS 的最短往返數字與 Python 相同，但記法門檻不同（`1e-7` vs `1e-05`、`1e+16` 的門檻、`1` vs `1.0`），而且 JS 沒有整數型別，`large_arc`、`sweep` 在 Python 是 int。另外 Python 的 `json.dumps` 預設會把 NaN 寫成 `NaN`，TS 寫出器則拋錯，兩邊失敗方式不同。
- **決定**：TS 的 `dumps` 自己排版（每層一格縮排、鍵依 Unicode 碼點排序、字串用 `JSON.stringify`），浮點數用 `py_repr`：由 `toExponential()` 取最短位數，依 CPython `format_float_short` 的規則「`decpt <= -4` 或 `decpt > 16` 用指數記法，指數至少兩位」還原 repr；整數欄位是封閉清單 `INT_KEYS`：第一階段 `{large_arc, sweep}`（v2 expected 檔中唯一的整數葉節點，各 74 處，已驗證），第二階段加上 M4 的 `interval`；新增整數欄位必須同時加進清單與 `rules.json` 的 `int_keys`。Python 側的寫出器加上 `allow_nan=False`（含 C 編碼器設定），NaN／Infinity 在兩邊都是例外（Python `ValueError`、TS `Error`），誰都不寫出 `NaN`。測試：對每個 expected 檔做 `dumps(JSON.parse(text)) + "\n" === text`。
- **理由**：比對是數值的，記法只影響位元確定性；但位元確定性是每個實作各自的承諾，而且同一份文件由兩邊寫出位元相同，是最便宜的寫出器驗證。NaN 在合約下不可能出現（§7.1 第 6 列），但真出現時兩邊要用同一種方式失敗。

## D53 SVG 寫出器與 Python 逐字相同；四位小數的平手採 round-half-even，以整數算術精確處理（合約 §5.4.6）

- **問題**：Python `f"{x:.4f}"` 對二進位值精確平手採 round-half-even，JS `toFixed(4)` 平手往上取；平手只在 `x·32` 為奇整數時發生（例如 0.03125），而奇整數 `x·32` 可以大到 |x| < 2^48，用 `x·1e4` 浮點相乘只在 |x| < 9e11 內精確。
- **決定**：`fmt` 先偵測平手（`Number.isInteger(x·32)` 且為奇數），再用 BigInt 做 `j = |x|·32`、`n2 = j·625`（= |x|·10⁴·2，精確）、`f = n2 div 2`、偶數規則取整、以整數除以 10⁴ 組字串；`|x| ≥ 1e21` 用 `BigInt(x)` 印完整位數；其餘用 `toFixed(4)`。手算：`fmt(0.03125) = "0.0312"`、`fmt(0.09375) = "0.0938"`、`fmt(-0.03125) = "-0.0312"`。元素字串、群組 id、順序、樣式與 Python 寫出器一字不差（含 M4 的隱藏線子群組與 M6 的光源子群組）。跨實作的 SVG 逐字比對是開發工具 `tools/compare_svg.py`，不是 CI 閘門（CI 閘門是 JSON 一致性測試集）。

## D54 比對規則單一來源 `tests/conformance/rules.json`；比對器的任何修改都是版本化的（合約 §5.4.8、§5.0.8）

- **規格**：§7.5「TypeScript 移植必須全數通過」、README 規則 2、3。
- **決定**：比對器常數（1e-6 mm、1e-9 相對、哪些鍵是 mm 座標、`arcs`／`ellipses` 容器、弧線項目裡的非 mm 鍵、`construction.segments[].points` 類路徑、整數鍵、逐案例的 `case_overrides`，以及 M4 的 `runs_rule`）寫進 `rules.json`；Python 測試保留自己的常數並斷言與檔案相等，TS 執行器直接讀檔。TS 執行器直接讀取倉庫的 `cases/` 與 `expected/`，絕不複製、絕不產生 expected。`rules.json` 的任何改動都經 `tools/regen_conformance.py --rules-only --reason` 在 `CHANGELOG.md` 追加一筆 `## v<N>`（「比對器修訂，expected 未變」），版本號照樣遞增。M7 的這一步（v3）**先於** M4–M6 合併進主分支，所以 M4、M6 的比對規則直接加在 `rules.json` 裡（D67）。先前設計裡「作圖線端點可預先授權放寬到 §4 (i) 的上界」一條**撤回**：規格 §7.5 與 README 把它定在 1e-6 mm，探針也沒發現需要；真遇到就走漂移規則。
- **理由**：M4–M6 新增可畫圖形時只改一個檔，兩個比對器不會漂移；比對器放寬若不進 CHANGELOG，Python 的閘門就會被悄悄鬆掉。

## D55 快捷方案的取捨（合約 §5.4.11）

- **規格**：§8 只換相機 < 100 ms；D17 把達標延到 M7，並點名兩個候選手段：更精簡的記錄形狀、編譯式格式化。
- **決定**：精簡記錄形狀**不可**用在 §6.2 文件（只准當 B 段私有暫存，且要有基準數據支持）；編譯式／查表式數字格式化**可以**，條件是證明與 `fmt` 完全相同。另外：每幀合併指標事件只算一次（必要）、Web Worker（可選）可以；拖曳期間把寫出器**原封不動的 SVG 文字**改用 `<img src=blob:>` 顯示、放手後回到 DOM 疊層（可選）可以——畫面仍是寫出器的輸出，只是瀏覽器的繪製路徑不同；拖曳期間以 `umbra=False` 略過本影、關閉消隱也可以（兩者都是合約定義的開關，關閉狀態仍是合約文件）；「拖曳預覽」降取樣／略過自我驗證／略過標籤、跨相機快取 B 段、用 DOM/Canvas 直接畫而不經 SVG 寫出器、用 three.js 相機矩陣當 P、float32、three.js shadow map 一律不可。任何會動到位元確定性、A 段與相機無關、文件欄位可移植三條不變式的手段，不論多快都拒絕。
- **理由**：看到的就是下載的；文件是合約，不能有「預覽品質」版本。基準場景的 SVG 有 1.96 MB、約 3 萬個元素，每幀 `innerHTML` 在任何瀏覽器都遠超 100 ms，所以 UI 的即時性要以五個範例場景驗收、基準場景另記 `dom ms`。

## D56 網頁 UI：three.js 只負責顯示，相機與陰影皆來自移植核心；相機區塊一律明確建構（合約 §5.4.10）

- **規格**：§9「網頁 UI 用 three.js 顯示場景，但陰影一律用移植核心計算，不用 three.js 的 shadow map」。

## D62 STEP 的 mm → m 轉換只有一個函數 `to_metres(x) = x / 1000.0`；未宣告單位視為 mm 並記備註；其他單位不支援（合約 §5.5.3）

- **規格**：場景 `units` 必須是 `"m"`；STEP 慣例預設 mm。
- **問題**：第一版設計同時寫了「除以 1000」和「乘以係數 0.001」，實作者照後者寫就會失去位元相同：`300*0.001 = 0.30000000000000004`、`9*0.001 = 0.009000000000000001`、`1001*0.001 = 1.0010000000000001`（[-10000, 10000] 內有 2676 個整數不同）。
- **決定**：長度單位只接受 `SI_UNIT(.MILLI., .METRE.)`（`unit_divisor = 1000.0`）與 `SI_UNIT($, .METRE.)`（`1.0`）；所有長度一律經 `to_metres(x, unit_divisor) = float(x) / unit_divisor + 0.0`，報告欄位叫 `unit_divisor`，合約裡沒有「係數」；沒有宣告長度單位時視為 mm 並記 `STEP_UNIT_ASSUMED_MM`；`CONVERSION_BASED_UNIT`（英吋等）或其他前綴回報 `StepError`「unsupported: length unit」。平面角：弧度或 `DEGREE` 的 `CONVERSION_BASED_UNIT`（讀檔內的換算係數），只用在圓錐半角的一致性檢查。
- **理由**：IEEE 除法是正確捨入，所以凡是 double 能精確表示的毫米值（整數、`0.5` 這類二進位分數）除以 1000 後**恰好**等於公尺字面值的 double（`300./1000. == 0.3`、`0.5/1000. == 0.0005`），這正是驗收案例能與 `expected/example_basic.json` 位元相同的原因。這個保證**不**涵蓋不能精確表示的小數（`2.1/1000.0 != 0.0021`，十分位有 24% 不同），所以只承諾整數／二進位分數毫米值位元相同，其餘在 1 ulp 內；測試用 9 mm、1001 mm、0.5 mm 驗證。

## D63 原型採無相依的 Part-21 子集解析器；OCP 只當選用的網格化函數與夾具產生器；網格退路經 M5 的內嵌網格物件（合約 §5.5.2、§5.5.7、§5.5.11）

- **問題**：pythonocc-core 無法用 pip 安裝（只有 conda）；可 pip 的 `cadquery-ocp` wheel 67 MB、安裝後 158 MB、LGPL-2.1，而且數值只確定到 OCC 版本——實測 OCC 自己的讀取器把 1200 mm 高圓錐的頂點重建成 (0, 0, 1.43e-9)，因為檔案裡的半角只有 12 位有效數字；OCP 8 的 API 名稱也和 7.x 不同（`TopoDS.Face` 而非 `Face_s`、`Bnd_Box.CornerMin/Max`）。
- **決定**：路線 (b)：`castplane/io/part21.py`（單一正規表達式的分詞器，註解與空白是它的第一個分支，所以字串裡的 `/*` 不會被誤刪；實體表；純標準函式庫）加 `castplane/io/step.py`（單位、放置、四種辨識器）。路線 (a) 的 OCP 只在選用 extra `step` 裡做兩件事：`tessellate_step` 把實體以 `BRepMesh_IncrementalMesh` 展成三角網格（實測 OCC 8.0：圓柱 170 節點／164 三角形、截頭圓錐 400／598、方塊 24／12、球 1447／2836；`isInParallel = False`；單位從建立 reader 之後的 `Interface_Static` 讀取，鍵名 `cascade_unit`），以及 `tools/make_step_fixtures.py` 產生夾具。**彙整修正**：M5 的內嵌網格鍵名（`data: {vertices, faces, smooth_groups}`）已在同一份合約裡定案，而且 M8 排在 M5 之後實作，所以 `fallback: "mesh"` 直接啟用：辨識不出的實體經 `mesh_object_from_triangles` 變成 M5 的 `mesh` 物件（公尺、未焊接、M5 預設 1e-6 m 的焊接會把逐面接縫合起來）並記 `STEP_SOLID_TESSELLATED`；`mesh` 物件的 `path` 以 `.step/.stp` 結尾時直接走網格化（不做解析辨識）。原設計「M5 定案前一律拒絕」的條款撤銷。實測原型：夾具約 2–3 ms，200 個實體 1.25 MB 0.63 s。

## D64 辨識規則只看面型別簽章與封閉實體，**完全不讀任何方向正負號**；圓錐頂點取拓撲頂點；圓柱軸向上標準化；球取恆等座標系；方塊配對不分正負；Euler 反解先把 −0.0 正規化（合約 §5.5.4、§5.5.5）

- **規格**：§5.6 只說解析曲面接圓錐曲線路徑。
- **問題**：審查用 OCC 8.0 實測：方塊的兩個對面寫的是**同一個** `PLANE` 法線方向（`#17` 與 `#137` 都是 `(0.866, 0.5, 0)`），只靠 `ADVANCED_FACE.same_sense` 的 `.T.`/`.F.` 區分；第一版「三對反平行法線」的規則對自己的夾具就辨識失敗。另外 OCC 會寫 `-0.`（`DIRECTION('',(1.,0.,-0.))`），`atan2(-0.0, -1)` 回 −180°，會讓同一個 180° 座標系在不同路徑下得到 ±180。
- **決定**：(1) 不讀 `same_sense`、迴圈方向、也不讀 `PLANE` 軸的正負號——所有判定只用 `|n × a|`、`|n_i × n_j|` 與位置差。方塊規則改為：六個平面依「方向（不分正負）」分成剛好三組、每組兩面且位置沿該方向不同、三組方向兩兩垂直、去重後剛好八個頂點；座標軸的正負由指定順序的第一個非零分量決定，平手取實體編號最小者；`position` 為底面中心（實測夾具：`size [1.00000000000002, 0.8000000000003888, 0.6]`、`rz = 30.000000000012566`）。(2) 圓錐的頂點取圓錐面上不在底面平面的 `VERTEX_POINT`（檔案裡是精確值），`semi_angle` 只做一致性檢查；底半徑取底面迴圈的 `CIRCLE` 半徑。(3) 圓柱的軸翻成向上（`a_z > 0`，水平時依 `a_x`、最後 `a_y < 0` 嚴格比較），`e2 = a × e1` 保持右手系，但 `e1` 沿用檔案的 `ref_direction`（`buried_cylinder_tilted` 的驗收證明它能回到 `conics[].circle.e1`）；因此 OCC 以 −z 軸寫出的圓柱展開成 `rotation_deg [0, 0, 180]`——同一個實體，只有 `circle.e1/e2` 與 `theta` 不同，所有具名點與多邊形相同（實測）。(4) 球沒有本徵座標系，一律用恆等座標系：`position = c − r·ẑ`、`rotation_deg [0,0,0]`，與內嵌球的 §2.6 退路一致（第一版沿用檔案座標系，會把以 −z 軸寫出的球錨在頂點）。(5) `rotation_deg` 由 `euler_zyx_deg(R)` 反解：先把九個元素 `+ 0.0`，再 `ry = atan2(−R₂₀, hypot(R₀₀, R₁₀))`、`rz = atan2(R₁₀, R₀₀)`、`rx = atan2(R₂₁, R₂₂)`，萬向鎖時 `rz = 0`、`rx = atan2(s_y·R₀₁, R₁₁)`；結果在 (−180°, 180°]，180° 的座標系永遠得到 `+180.0`（實測）；不把接近零的角度或尺寸捏成零（M5 的 glTF 匯入器用同一個反解）。容差每檔一次、以 mm 計：`extent_mm = max(1, k·max|座標|)`、`tol = 1e-6·extent_mm / k`（公尺檔 k = 1000），方向 `1e-7`，只用於分類，組件恆等檢查也用它。
- **理由**：方向與迴圈定向是 B-rep 讀取器最容易出錯的部分，而四種基元根本不需要它；頂點與半徑在檔案裡是精確數字，半角不是。軸向上標準化讓匯入的柱子底面在下，符合 §2.1「錨點在底面中心」。實測：圓柱、球、圓錐展開後與參數化物件**位元相同**；旋轉 30° 的方塊與傾斜圓柱在 1e-9 內一致，渲染結果通過一致性比對（最大差約 3e-11 mm）。

## D65 匯入器的備註與錯誤自成一套；一致性測試集不變；CLI 寫出原始場景（合約 §5.5.6、§5.5.8、§5.5.10、§5.0.2）

## D66 組件只接受恆等變換；多實體命名 `<id>_<k>`；夾具產生器把 PRODUCT 名稱正規化（合約 §5.5.4、§5.5.6、§5.5.9）

- **規格**：簡報把「單一放置以外的組件變換」列為範圍外。
- **決定**：OpenCascade 把任何多實體 compound 都寫成組件（`NEXT_ASSEMBLY_USAGE_OCCURRENCE` + `ITEM_DEFINED_TRANSFORMATION`），所以不能一律拒絕：每個 `ITEM_DEFINED_TRANSFORMATION` 的兩個放置必須相等（恆等），否則回報 unsupported；實體座標一律視為絕對座標。多個實體時 id 為 `<id>_<k>`（實體編號遞增順序），`solid: k` 可只取一個（必須是整數，布林與浮點數拒絕）；不用 STEP 的產品名稱當 id。夾具產生器一次在同一個程序內依固定順序寫出整組檔案，並把 `FILE_NAME` 時間戳、作者、組織與**每個 `PRODUCT` 的名稱／id**（OCC 寫的是程序內計數器 `'Open CASCADE STEP translator 8.0 7'`、`'… 7.1'`）改寫成固定字串，`--check` 以同樣方式重產並比對位元。
- **理由**：恆等組件是實務上最常見的多實體檔；變換鏈的語意需要參考讀取器驗證，留作後續項目。PRODUCT 計數器不正規化的話，產生子集或換順序就無法位元重現。

## D67 【彙整】一致性測試集的版本序列與合併順序：v3 比對器（M7）→ v4 鍵新增重產（M4）→ v5 網格案例（M5）→ v6 多光源案例（M6）；M8 不加案例；M7 第二階段在 v6 上收尾（合約 §5.0.8、§5 前言）

- **問題**：五份設計各自寫「下一個版本」：M7 說 v3 是比對器修訂，M4 說 v3 是整組重產，M5、M6 都說「合併時指定」；M4 說整組重產「在合併後的分支上做一次」，M5 說「M4 先重產、M5 再 rebase」；每個工作樹裡的 `--case` 都會讓工具追加一筆版本。
- **決定**：合併順序固定為 M7 第 1 步（只有 `rules.json`、`--rules-only`、v3）→ M4（在主分支合併時做一次整組鍵新增重產，v4，先用 `--strip-new-keys` 證明零改動；M4 的 9 個新案例同一筆）→ M5（rebase 後只用 `--case` 加 3 個案例，v5）→ M6（4 個案例，v6）→ M8（不加案例）→ M7 第二階段（兩個執行器在 v6 全綠，記在 v6 那一筆）。工作樹內可以隨意跑工具，但合併時把工作樹產生的 CHANGELOG 條目**合併成該里程碑一筆**，版本號由主分支上的 `next_version` 指定。M4 的 `runs_rule`、`hidden_polylines`、`interval`，M6 的 `constructions` 路徑都直接加在 `rules.json`（v3 先進主分支就是為了這個），Python 比對器與 TS 執行器讀同一個檔。
- **理由**：只有一個主分支的版本序列才不會讓兩個工作樹互相覆蓋 expected 檔與版本號；比對器先定案，之後的所有重產與新案例都在最終的比對規則下驗證。

## D69 【彙整】§3.1 文件與命名的統一：`shadows[]` 順序、`constructions` 含 `per_receiver`、保留 id、由右往左的點名文法、`INT_KEYS`、網格遮擋物、SVG 子群組順序（合約 §5.0.3–§5.0.6、§5.1.3.1、§5.1.6.2、§5.2.5、§5.3.1、§5.3.5）

- **問題**：M4 要求 `shadows[]` 依受影面 → 光源 → 施影者輸出，M6 寫的是物件優先、光源次之；M4 的 `construction.per_receiver` 與 M6 的 `constructions{<light>}` 沒有互相提到；M4 的 `cast_shadow.hidden` / `objects.hidden` 與 M6 的 `cast_shadow.umbra` / `form_shadow.core` 會與同名的物件、受影面或光源 id 撞群組 id；M6 的名稱由右往左對照光源 id 解析，M4 又在最右邊加受影面 id；M4 的 `interval` 是整數但 M7 的 `INT_KEYS` 只有 `large_arc`、`sweep`；M4 的通用網格遮擋物用 `obj["mesh"]` 的面，M5 說應該用 `triangles`；M5 的非流形退路沒有說怎麼對有界受影面裁切；M6 的「有效光源」與 M4 的逐受影面 `lit` 沒有對上；兩個里程碑各自規定層內子群組的位置。
- **決定**：(1) `shadows[]`、A 段紀錄順序一律是受影面（場景順序）→ 光源（場景順序）→ 施影者（物件後接其他板）；單光源單受影面時與 v1 相同，M6 的「第一個物件的紀錄列出所有光源」不變量改寫為「`receivers[0]` 上第一個施影者的紀錄依場景順序列出所有光源」。(2) `constructions[<light>]` 的形狀就是 M4 的 `construction` 區塊（含 `per_receiver`），`construction` 是 `lights[0]` 那一塊的別名；`rules.json` 把 `constructions.*.segments[].points` 與兩層的 `per_receiver.*.segments[].points` 都列為 mm 路徑。(3) 保留 id：`hidden` 任何時候都不能當物件、受影面、光源 id；多光源場景再拒絕光源 id `umbra`、`core` 與物件 id `core`；受影面 id 與物件 id、光源 id 兩兩不重複。(4) 點名文法 `<obj>.<stem>[.<light>][.shadow.<light> | .foot][.<r>]` 由右往左對照已知的受影面 id、光源 id 解析；標籤規則統一為「任一段是 `shadow` 或 `foot`、或開頭是 `s<k>`／`og<k>` 就不標」。(5) `INT_KEYS = {large_arc, sweep, interval}`，與 `rules.json` 的 `int_keys` 相同。(6) M4 的通用遮擋物對帶 `triangles` 的紀錄（所有 M5 網格）用三角面，其他種類才用 `obj["mesh"]` 的面。(7) 非流形退路對每個受影面 `clipped[r] = None`，逐面迴圈經 `shadow_loop` 後再做 D22 的 bounds 裁切。(8) `umbra[].lights` 是該受影面上 `lit` 為真的光源；映回受影面用該面的單應。(9) 平面板在多光源下視為單面多面體（逐光源 `form_shadow` 項目加 `form_shadow_core`）。(10) 層內子群組順序：`*.hidden`（有消隱時最先）→ 各光源群組 → `cast_shadow.umbra`／`form_shadow.core`；非預設受影面的作圖線畫在同樣的 `LP`／`FQ`／`PQ` 群組。(11) API 簽名合併：`project_scene(scene, A, camera=None, umbra=True)`、`compose(scene, B, hidden_lines=None)`、`render(scene, camera=None, hidden_lines=None, hidden_style=None, umbra=True)`、`write_svg(doc, layers=None, hidden_style="dashed")`。(12) M6 的「單光源文件逐位元等於 v1」改為「等於 M4 合併後的 v4 形狀」（M4 加的是無條件鍵且先合併）。

## D70 多次出入無窮遠的影子迴圈：無窮遠弧的角度配對（合約 §2.5、§5.1.3.3；審查發現 m4-geometry#0、determinism-perf#0）

- **問題**：D7 把每個出射方向 D_out 與**迴圈順序上的**下一個入射方向 D_in 配對，再逆時針掃 Δθ ∈ (0, 2π]。只有當「過光源且平行於受影面的平面」切迴圈兩次時這才正確（凸多面體、地面上的直立稜柱、燈在凹口內而板在封閉臂後方的情形：迴圈順序與角度順序一致）。當該平面切迴圈 2p ≥ 4 次——凹形施影體、燈在兩臂之間：站在地面上的拱、燈低於楣；側躺的 U 形稜柱、燈在凹口內；地面上的 U 形稜柱、牆在**開口**後方；跨過「過燈且平行於牆的平面」的 U 形稜柱——兩對交點在角度上交錯，迴圈順序配對掃出 289° + 242° 蓋滿整個圓，nonzero 填滿整個地面或整塊板（§5.1.3.3 的錨點規則會忠實地填滿板，有界受影面又不發警告）。§5.1.3.3「錨點規則使凹稜柱 ≥ 180° 的弧精確」的說法依賴這些弧，在此情形下不成立。
- **決定**：迴圈是光源方向球面上的封閉曲線，影子在其左側，光平面是赤道；沿赤道逆時針（繞 n）走，出射交點使實體命中數 +1、入射交點 −1，所以無窮遠處落在影子中的方向集合——即無窮遠弧——完全由迴圈自己的交點決定，與原點、參考點無關。`shadow.shadow_loop`：(1) p ≤ 1 保留 v1/v2 逐字程式碼（位元相同；50 個 conformance 案例沒有 p ≥ 2 的迴圈，dry run 0 變更）；(2) p ≥ 2 時把 2p 個交點依繞 n 的角度排序（地面用 (x, y) 的 atan2，有 frame 的受影面用 (e1, e2)，化到 [0, 2π)；角度相等時入射在前），從第一個累計層級最小的交點開始，出射 = 「(」、入射 = 「)」做括號配對——對球面上單純的迴圈，就是每個 D_out 配**角度上下一個** D_in；(3) 每段弧由 D_out 逆時針掃到配對的 D_in（v1 逐字算式 (θ_in − θ_out) mod 2π，重合時仍為 2π，再加上與展開排序差相差的整圈數；與迴圈順序配對一致時位元相同），細分規則 ceil(Δθ/60°) 與 ("arc", k) 來源不變；(4) 把有限鏈 in → … → out 經配對的弧重新串接，**每個循環輸出一個迴圈**（含起點的循環在前、沿用原頂點順序，其餘依其最小鏈序），放在結果的新鍵 `loops`（p ≤ 1 時是單元素串列、別名頂層陣列，空結果亦然；頂層陣列永遠是第一個分量）；`_shadow_record`、`_fallback_shadow_record`、`_caster_record` 把每個分量當成紀錄的一個迴圈畫出（有界受影面逐分量做 bounds 裁切，交點名稱 `s<k>` 跨分量依首次出現編號，`loops`／`polygons`／`polygon_edges` 保持平行）。**不採用**審查者提議的「被捨棄頂點 S[:3] 方位角的帶號和」：那個方位角是從受影面座標原點量的，同一個拱平移 (0, 6, 0) 後得到影子的補集；本配對只用方向，故平移、旋轉不變。有限點的環繞數只取決於該迴圈所有弧的總掃角，所以只要迴圈的區域留下某個赤道方向在外（最小層級即外側），填色就精確；在光平面內把光源整個圍住的迴圈需要外部基準層級——**基元就能產生**（螺旋稜柱、燈在內部半高處），見下方「修訂（第二輪審查）」。`curved.shadow_polygon_h` 不變（凸實體的輪廓最多與赤道相交兩次）。§2.5 與 D7 以引用方式修訂；TypeScript 移植（`src/shadow.ts`）必須逐字鏡射 (1)–(4)（相同的排序鍵、平手規則、最小層級起點、循環順序）。
- **驗證**：`tests/test_arc_pairing.py`（拱形板的解析影子、合成交點型樣含巢狀與重合、平移／旋轉不變性、四個 v7 候選場景對光線投射 IoU ≥ 0.99 或空影子）、`tests/test_raycast.py::test_multi_crossing_loops_match_raycast_reference`（12 個隨機拱場景，直立或懸空、繞 z 旋轉、燈在開口內）。驗收數字：拱 IoU 0.075 → 1.000，側躺 U 0.458 → 1.000，U 與開口後方的牆 0.456 → 0.994，跨光平面的 U 在牆上 15 m² → 空，凹星加牆 0.299 → 1.000；既有 50 個 conformance 案例位元相同；場景放在 `tests/fixtures/v7_candidates/`。

## D71 `picture_plane` 是相機的第三種寫法；換算在 B 段之前，A、B 段與 `camera_matrix` 的慣例（含 det R = −1）不變（合約 §2.0、§2.2 修訂段落，§5.7.1、§5.7.2）

- **規格**：規格 v0.2 §4.1：相機區塊多一種寫法 `position` + `picture_plane {normal, offset, up?}`，與 `target`、`yaw/pitch` 三擇一；換算成 `target` 形式後完全走現有的 `camera_matrix`。
- **問題**：既有的驗證把相機寫法限定為兩種，`load_scene` 會把 `roll_deg` 預設為 0；若第三種寫法的驗證輸出也帶 `roll_deg: 0`，網頁「Download scene」寫回的場景與 `pipeline._resolve_camera` 再驗證時就會因「`roll_deg` 與 `picture_plane` 並存」被拒。法線的正負號與長度、平面通過眼睛、`up` 與法線平行都需要明確的錯誤欄位。
- **決定**：`camera` 恰好一種寫法，同時給兩種以上回報 `SceneError("camera")`；`picture_plane` 形式下出現 `roll_deg`（含 0）回報 `camera.roll_deg`；法線長度 ≤ 1e-12 回報 `.normal`；`|n̂·E + offset/|n|| ≤ 1e-9` m（平面通過眼睛）回報 `.offset`；`up` 正規化後投影到平面的長度 ≤ 1e-9（零向量、平行法線）回報 `.up`；非有限數照舊回報各分量。驗證輸出保留輸入的數值（不正規化）且**不含** `roll_deg`，所以驗證兩次結果相同。`castplane/picture_plane.py` 的 `resolve_picture_plane` 依序算 `s = n̂·E + ô`、`D = |s|`、`f = −sign(s)·n̂`、`Q = E − s·n̂`、`target = E + f`，產生一個 `target` 形式區塊；`camera_forward` 與 `camera_matrix` 開頭遇到 `picture_plane` 先換算，之後完全走原本的程式碼。TypeScript 以相同名稱鏡射。
- **理由**：核心只多一個常數時間的前置換算，A 段不碰相機、B 段與作圖管線一行不改，D14 的相機慣例自然保留；驗證輸出可重複驗證，網頁與命令列之間的場景檔就能來回而不失真。

## D72 板子為主：網頁狀態是（方向、g、D、平移、滾轉、up），眼睛與平面常數由它算出且唯讀；核心只看相機區塊（合約 §5.6.0、§5.7.7）

- **規格**：規格 v0.2 §1、§4.2：使用者只操作板子的方向 f 與離場景的距離 g；眼睛 E = P − (g + D)·f + L 由此算出，唯讀；板子狀態只在網頁，核心不知道。
- **問題**：若網頁直接持有 E 或讓 E 可拖，就會出現「拖 E」「繞 E 轉頭」等多套互相衝突的操作模型；若把板子狀態寫進場景格式，核心與一致性測試集就要多認識一套只有介面才需要的資料。
- **決定**：`web/src/rig.ts` 的狀態為 `{f, up | null, g, D, a, b, rho_deg, focal_length_mm}` 加上旋轉中心的選擇；E、Q、平面常數 c = f·P − g、R = g + D 都是每次重算的衍生量。滾轉前的基底 (r₀, u₀) 取 `up` 或世界 +z 的投影，f 平行 z（`|f × z| ≤ 1e-9`，與合約 §2.2 同一個判定）時取 +y，所以鎖水平且 ρ = 0 時與 `camera_matrix` 的預設基底完全相同。換成核心區塊時寫 `position = E`、`normal = f`、`offset = −c`、`up = u`（鎖水平且 ρ = 0 時省略）。命中測試永遠不回傳 E。場景載入時的換算（載入規則）把任何相機換成這組狀態：f 取 forward，D 取 `picture_plane` 的距離（其他形式 4 m），眼睛偏離旋轉中心軸線的部分成為平移；未夾限時畫面不變。
- **理由**：一組最小狀態涵蓋全部操作，眼睛的位置永遠由同一條公式決定，不會有兩條路徑互相打架；核心只看到一個普通的相機區塊，Python 命令列可以重現網頁的每一張圖。

## D73 視角固定、D 只由滑桿改變：焦距與片幅不隨平面變；箭頭移動板子時眼睛一起移動，D 滑桿移動眼睛時板子不動，兩者都靠改變觀看距離 R 來改變畫面（合約 §5.7.8 第 4、5、8、9 項）

- **規格**：規格 v0.2 §1 的模型事實 1、2：眼睛不動時平移板子只會等比縮放畫面；本模型讓眼睛固定在板子後方 D 隨板子移動。焦距與片幅不隨圓環、箭頭改變；D 只由焦距旁的滑桿改變。
- **問題**：「拉近」有三種可能的意思——焦距（等比放大，遠近比例不變）、移動板子（只縮放）、移動眼睛（透視改變）；若箭頭、滾輪、焦距、D 各自改變不同的量又互相牽動，使用者無法預期畫面，畫框在 3D 中的實際大小也會跟著亂跳。
- **決定**：箭頭與右窗滾輪（及雙指捏合）只改 g（D 不變，眼睛與板子一起沿 f 移動）；D 滑桿只改 D（g、c 不變，板子不動，眼睛沿 −f 移動，畫框公尺尺寸按比例變）；焦距滑桿只改視野與畫框，眼睛與板子都不動，保留 M7 的對數範圍 [8, 400] mm（規格 v0.2 的 12–80 mm 是 demo 的範圍，倉庫場景用 35 mm 等其他值）。R = g + D 夾在 [0.8, 40] m，D 夾在 [0.5, 12] m 且同時滿足 R 的範圍。初始狀態取場景相機經載入規則換算的結果；規格 v0.2 §4.2 的 `y = 2`、D = 4 m 起始狀態可用方程式 `y=2` 重現。
- **理由**：每個控制項只改一個量，畫面的變化就可以預期：只有改變 R 才改變透視強弱，焦距永遠是等比放大；畫框的實際大小只在調 D 或焦距時改變，拖把手時不會變。

## D74 `roll_deg` 的參考方向取 `camera_matrix` 的預設 up（含 +y 後備）；`picture_plane` 形式不發 `CAMERA_LOOKING_ALONG_UP`（合約 §2.2 修訂段落、§5.7.3）

- **規格**：規格 v0.2 §4.1：`roll_deg` 取「`camera_matrix` 由 f 算出的預設 up」到畫框 `up` 的有號角，繞 f 量測；`picture_plane` 形式不發 `CAMERA_LOOKING_ALONG_UP`。附錄 A.5：必須抑制，而不是新增警告代碼。
- **問題**：「有號角」的正負號若與 `camera_matrix` 的滾轉慣例（正滾轉讓畫面內容順時針轉）相反，畫面會轉錯方向；預設 up 的判定若與 `camera_matrix` 用不同的向量或門檻，在 f 接近 z 軸時兩邊會一邊用 +z、一邊用 +y，畫框差 90° 左右。水平的板子（由上往下看）在既有規則下一定發警告，但畫框的 up 其實已經明確。
- **決定**：取 `fwd = camera_forward(換算後區塊)`（正是 `camera_matrix` 會用的向量），預設基底完全照合約 §2.2：`|fwd × z| ≤ 1e-9` 時改用 +y，`right₀ = normalize(fwd × up_world)`、`up₀ = right₀ × fwd`；畫框 up `u` 為給定的 `up`（省略時為 `up_world`）投影到垂直 fwd 的平面再正規化；`ρ = degrees(atan2(−u·right₀, u·up₀))`，代入 §2.2 的滾轉公式正好得到 `up' = u`。`picture_plane` 形式的區塊在 `camera_matrix` 不附加 `CAMERA_LOOKING_ALONG_UP`（+y 後備仍用作參考方向）；`target` 與 `yaw/pitch` 形式照舊警告。警告代碼維持 18 個。
- **理由**：同一個向量、同一個門檻、同一個滾轉公式，兩邊不可能不一致；警告的用意是告訴使用者「up 是後備值、畫面方向可能不是你要的」，而 `picture_plane` 的畫框 up 是明確的（給定或依規則預設），這個提醒沒有資訊量。封閉的警告清單不動，就不是合約變更。

## D75 幾何文件的新鍵只在 `picture_plane` 形式出現，既有 expected 不重新產生（合約 §3.1 修訂段落、§5.7.4、§5.7.14）

- **規格**：規格 v0.2 §4.1、附錄 A.3：幾何文件記錄正規化後的 `picture_plane`，另附 D、Q、畫框公尺尺寸與方程式字串；其他 60 個既有案例不變。
- **問題**：比對規則要求鍵集合完全相同；若新鍵無條件出現（像 M4 的 `receivers`），60 個 expected 檔都要整組重新產生（D28 的 v4）。新鍵的數值若算成 mm 鍵、或方程式字串在兩個建置之間捨入不同，比對器也會失敗。
- **決定**：只有以 `picture_plane` 相機算出的文件在 `camera` 區塊多一個鍵 `picture_plane = {normal: f, offset: −f·Q, up: u, distance: D, foot: Q, frame_m: [frame_w·D/focal, frame_h·D/focal], equation}`（`normal` 一律是由眼睛指向平面的單位法線，與輸入的正負號、長度無關）；其他文件逐位元不變，沿用 M6「多光源鍵只出現在多光源文件」的前例。數值走既有的相對 1e-9 規則（沒有 mm 鍵），`equation` 完全相等，`rules.json` 不改。方程式字串：法線平行座標軸（`||n_i| − 1| < 1e-9`）時寫 `y = 2.00`（數值依法線正負號換算、兩位小數），否則第一個寫出的係數（`|係數| ≥ 5e-4`，與省略門檻相同，字串因此不會以負號開頭）取正、省略 `|係數| < 5e-4` 的項、係數與常數三位小數；捨入照 Python `format(v, ".2f")`（精確平手取偶數），`-0.00` 寫成 `0.00`；TypeScript 用 `fmt` 的精確平手規則重現（`toFixed` 平手進位，`0.125` 會得到 `0.13`）。一致性測試集 v7 → v8 只新增三個案例（垂直 `y = 2`、傾斜、水平 `z = 3` 由上往下），案例的方程式數值必須離捨入邊界至少 1e-6。
- **理由**：條件式的鍵讓舊文件一個位元都不動，不需要第二次整組重產；字串完全相等的比對最嚴格，所以捨入規則必須寫死到平手怎麼處理，案例也要避開邊界，兩個執行器才會在同一個 commit 上都通過。

## D76 環繞是整組繞旋轉中心的剛體轉動：抓點跟手指的符號規則、鎖水平預設、吸附整組貼齊、仰角夾 ±89.9°（合約 §5.7.8 第 1–3 項）

- **規格**：規格 v0.2 §5.2：靈敏度 κ = 0.32°/px；抓住圓環上的點，它跟著手指走；鎖水平時先繞世界 z 再改仰角，自由滾轉時繞旁觀相機的上、右軸；f 與座標軸夾角 < 5° 時整組貼齊。
- **問題**：只用螢幕位移的正負號決定轉向時，從板子背面或下方抓圓環會「越拉越反」；逐次累加的轉動會累積誤差並讓吸附來回跳動；鎖水平在 f = ±z 時「水平右軸」沒有定義；直接把仰角拖到 ±90° 會落在預設 up 的退化點上。
- **決定**：轉向由 `sgn(axis, dir, flip) = sign(±dir·(axis × w))` 決定（w 是按下時抓到的圓環點相對旋轉中心的向量，絕對值 < 1e-6 時取 +1）；每次移動都從按下時的狀態加上總位移重算。鎖水平：繞 z 轉 `sgn(z, r_c, 否)·Δx·κ`，再以轉後的鎖水平基底右軸 r₁（f = ±z 時用 +y 後備，所以有定義）把仰角改到 `clamp(p₀ + sgn(r₁, u_c, 是)·Δy·κ, ±89.9°)`；自由滾轉：繞 u_c、r_c 轉，`up` 同步旋轉。吸附以最小旋轉把 f（與 `up`）轉到精確的座標軸向量，所以一鍵視圖與吸附可到精確的 ±90°。g、D、平移、滾轉不變，所以眼睛對旋轉中心是剛體運動。右窗左拖用同一套規則、符號沿用 M7（−Δx·κ、往下拖眼睛升高）。鎖水平為預設，且「鎖水平」就等於 `up` 為空。
- **理由**：以抓點與旁觀相機軸的幾何關係決定轉向，不論從哪一側抓，抓點都跟著手指；從按下狀態重算讓吸附穩定、可逆；89.9° 的拖曳上限避開退化，而精確的 ±90° 仍可由吸附與一鍵視圖到達，而且 `picture_plane` 形式在那裡不會發警告（D74）。

## D77 取消自動移位與拖 E：旋轉中心沿 f 的深度永遠是 R，不會落在視點背後（合約 §5.6.0、§5.7.7、§5.7.12）

- **規格**：規格 v0.2 §1 的模型事實 3、4：沒有平移時旋轉中心在畫框正中央；平移垂直於 f，旋轉中心沿 f 的深度永遠是 R = g + D ≥ 0.8 m；先前草案的「拖 E」「自動移位」「繞 E 轉頭」已取消。
- **問題**：可拖的眼睛會讓旋轉中心跑到視點背後，於是需要「自動移位」把整組推回來，畫面在使用者沒有操作的情況下跳動；載入的相機（例如 yaw/pitch 形式）可能根本沒有對著場景中心，R 可能小於 0.8 甚至為負。
- **決定**：E 一律唯讀；R 的範圍 [0.8, 40] m 由每個操作的夾限維持（箭頭、滾輪、D 滑桿、方程式欄位），所以場景中心永遠在眼睛前方。載入規則在 R 超出範圍時把它夾回範圍內（眼睛與板子沿 f 移動）並提示「相機與場景中心的距離超出範圍，已調整」，D 超出滑桿範圍時同樣夾限並提示；未夾限時載入前後的畫面相同。方程式欄位除了 `g + D > 40` 之外，也拒絕 `g + D < 0.8`。
- **理由**：不變量 R ≥ 0.8 由操作本身保證，就不需要任何事後修補的自動行為；載入時的夾限與既有的 D 夾限是同一種「告知後調整」，使用者看得到原因。

## D78 右窗沿用 M7 的操作並對應板子模型：左拖＝圓環、滾輪＝箭頭（不是焦距）、右拖＝平移（不是更換旋轉中心）、滾轉滑桿沿視線滾轉（不是自由滾轉）；平移以滾轉前的基底記錄（合約 §5.4 實作註記、§5.7.8 第 2、5–7、10 項、§5.7.9）

- **規格**：規格 v0.2 §5.9：右窗的左拖、滾輪、右拖、Shift 拖、雙指手勢都對應到板子狀態；滾輪不等於焦距、平移不等於更換旋轉中心、滾轉不等於自由滾轉；規格 v0.2 §4.2：平移以滾轉前的基底記成 (a, b)。
- **問題**：M7 的右窗操作改的是 orbit 狀態（yaw、pitch、distance、target）；若 M10 照搬，滾輪會改變一個板子模型裡不存在的量，右拖會移動旋轉中心，滾轉滑桿也會與自由滾轉的 `up` 混在一起。平移若以滾轉後的基底記錄，調滾轉時眼睛會跟著移動。
- **決定**：右窗左拖＝圓環（合約 §5.7.8 第 2 項）；滾輪 `R ← R·exp(0.001·ΔY)`、捏合 `R ← R₀·d₀/d`，換成 g 並夾限、不吸附、不改焦距；右拖、Shift 拖、雙指移動＝平移，每像素公尺數 `k = R·(frame_h/focal)/H_px`，`ΔL = −Δx·k·r + Δy·k·u`，a、b 加上 ΔL 在 r₀、u₀ 上的分量，旋轉中心不變；滾轉滑桿只設 ρ，眼睛與板子不動。更換旋轉中心是另一個操作：保留 f、g、D、up、ρ，平移歸零（眼睛移到新中心的軸線上），不進復原堆疊。M7 的 `orbit.ts` 與其測試在 M9 不動；M10 在接上 `rig.ts` 的同一個變更裡停止用它驅動介面，測試維持綠燈，要刪除它須另做有紀錄的修訂。
- **理由**：使用者已經熟悉的手勢保持不變，只是改為作用在板子上；每個手勢對應板子模型的一個量，滾輪與焦距、平移與旋轉中心、滾轉與自由滾轉就不會混淆。滾轉前的基底讓環繞時平移跟著整組轉（眼睛仍對旋轉中心剛體運動），滾轉時基底不動（眼睛不動）。
- **後續**：右窗操作的部分（左拖、滾輪、右拖、Shift 拖、雙指）已由 D79 取消，右窗改為唯讀；本條對滾輪與焦距、平移與旋轉中心、滾轉與自由滾轉的區別，以及平移以滾轉前的基底記錄，仍然有效。

## D79 右窗唯讀、工具列預設：右窗的拖動與滾輪安靜地不做事，板子只在左窗與工具列操作；圖層與 Hidden lines、3D view 是頁面層級的預設狀態（修訂 D78；合約 §5.4 與 §5.7 實作註記）

- **規格**：規格 v0.2 §5.9（右窗唯讀）、§2.1（工具列預設）；修訂 D78 中「右窗的左拖、滾輪、右拖、Shift 拖、雙指手勢對應到板子狀態」的部分。
- **問題**：D78 讓兩個窗都能改相機：左窗拖把手、右窗沿用 M7 的手勢，同一件事有兩個入口，而且右窗是「結果」，使用者在看圖的時候手指一動就改了視角（觸控時一捲頁面就轉動，右鍵選單也被吃掉）。另一方面，頁面開啟時的勾選狀態取自場景檔的 `output.layers` 與 `output.hidden_lines`，載入每個範例都被重設，而且預設會把作圖線畫滿畫面，3D 畫布也先佔著算圖時間。
- **決定**：
  1. 右窗（`#stage`）唯讀：任何拖動（左、右、中鍵、Shift、觸控單指或雙指、手寫筆）與滾輪都不觸發任何操作，不報錯、不提示、不進復原堆疊、不改相機、不顯示抓取游標。右窗不呼叫 `preventDefault`，滾輪與觸控交給瀏覽器、頁面照常捲動（`#stage` 的 `touch-action` 回到預設，`#observer` 維持 `none`），也不再攔截右鍵選單；檔案拖放在整個頁面照舊有效。
  2. 板子與旁觀相機只在左窗操作（圓環、箭頭、空白處繞轉、滾輪縮放旁觀相機、點選物體當旋轉中心），再加上工具列與面板：焦距、D、滾轉滑桿、六個一鍵視圖、方程式欄位、復原、重設、鎖水平、旋轉中心選擇。
  3. 平移 (a, b) 不再能手動編輯：只來自載入規則，並在點選物體與一鍵視圖時歸零，其餘操作保留它。D78 對滾輪與焦距、平移與旋轉中心、滾轉與自由滾轉的區別，以及「平移以滾轉前的基底記錄」仍然有效。
  4. 工具列預設：頁面開啟時 horizon、objects、form_shadow、cast_shadow、labels 與 Hidden lines 勾選；construction（右窗下方的「作圖線」勾選框與它同步）與 3D view 不勾選，3D 畫布從第一格起隱藏且不繪製。這些是頁面層級的狀態，載入場景或範例後保持使用者設定的值，不再取場景的 `output.layers`、`output.hidden_lines`（場景檔欄位本身不變，命令列照舊使用）。Hidden style 選單只在 Hidden lines 勾選時可用。「Download SVG」用目前勾選的圖層，「Download JSON」與「Download scene」用目前的 Hidden lines 狀態。旁觀視角開關預設關閉，不變。
- **理由**：操作板子只留一個地方（左窗與工具列），右窗就成為穩定的結果畫面，看圖、捲頁、點右鍵都不會誤改視角；觸控裝置上右窗也不再搶走捲動。預設直接顯示完成的線稿（物體、地平線、陰影、標籤，被遮住的線依 Hidden style 畫出，預設為虛線），不被作圖線蓋滿；要看作圖過程再勾選 construction。3D view 預設關閉讓畫面乾淨，也省下一個 WebGL 畫面的算圖。勾選狀態屬於使用者的介面偏好，不屬於場景，所以載入另一個場景不該把它改回去。代價：旁觀視角關閉時沒有拖曳可以改相機（只剩滑桿、一鍵視圖與方程式），需要拖曳圓環與箭頭時打開旁觀視角；平移因此沒有手動入口，只能靠載入帶偏移的相機取得。
- **後續**：第 4 點最後一句「旁觀視角開關預設關閉，不變」，以及本條「代價」中「旁觀視角關閉時沒有拖曳」的前提，已由 D80 取代（旁觀視角預設顯示，開關改為「預覽」按鈕）；其餘仍然有效。

## D80 旁觀視角預設顯示，「旁觀視角」開關改為作圖畫面右上角的「預覽」按鈕（修訂 D79 與 M9 的開關決定；合約 §5.6.0、§5.6.3、§5.6.4 與 §5.6 實作註記）

- **規格**：規格 v0.2 §2.2（編輯畫面與預覽）、§2.1（旁觀視角一列）、§5.9、§7.2 的 M9 一列；修訂 D79 第 4 點最後一句「旁觀視角開關預設關閉，不變」，以及 M9 在合約 §5.6.3、§5.6.4 定下的「開關預設關閉、每個瀏覽器用 `localStorage["castplane.observer"]` 記住」。M9 的開關沒有獨立的 D 編號，它的條文在合約 §5.6。
- **問題**：D79 讓右窗唯讀，板子只能在左窗（旁觀視角）操作，但旁觀視角是一個預設關閉、還會被瀏覽器記住的勾選框。結果是頁面剛開啟時什麼都拖不動，要先找到並打開一個開關；而關閉的狀態又讓整個頁面沒有任何拖曳入口。「看完成的作圖」其實是暫時的看一眼，不是把一個功能關掉。
- **決定**：
  1. 取消「旁觀視角」勾選框。頁面一律以**編輯畫面**開啟：旁觀視角窗格預設顯示，在作圖畫面左側（頁面寬度小於 880 px 時改為上下堆疊，旁觀視角在上），也就是原本開關打開時的版面。
  2. 作圖畫面右上角新增切換鈕「預覽」（`aria-pressed`）。按下後旁觀視角窗格、工具列的「整體顯示」與狀態列的 `obs ms` 都隱藏，作圖畫面佔滿全寬；這就是原本「開關關閉」的狀態。預覽時按鈕顯示「返回編輯」，再按一次或按 Esc 回到編輯畫面（旁觀視角重新顯示）。
  3. 預覽時不能拖曳板子（右窗唯讀，D79；把手在旁觀視角裡）；滑桿（焦距、D、滾轉）、六個一鍵視圖、方程式欄位、復原、重設照常可用。
  4. M9 的「開關關閉＝M7 頁面」恆等式照舊成立，只是改名：預覽時的版面、算圖迴圈與輸出和 M7 頁面相同；同一台相機下，疊層 SVG 與下載的 SVG、JSON 在編輯畫面與預覽之間逐位元相同。
  5. 不再記憶：頁面每次都從編輯畫面開始，舊的 `castplane.observer` 不讀也不寫（瀏覽器裡殘留的值直接忽略），預覽狀態也不存。
  6. D79 的其餘部分（右窗唯讀、板子與旁觀相機只在左窗與工具列操作、平移只來自載入規則、工具列預設）不變。核心、文件位元組與一致性測試集都沒有變動。
- **理由**：D79 之後，旁觀視角就是操作板子的地方，應該預設就在，而不是要使用者去打開的附加功能；「看完成的圖」是暫時的檢視動作，用一個「預覽／返回編輯」的按鈕表達，比一個關掉功能的勾選框貼近用途，而且只有一個控制，不會把頁面留在沒有拖曳入口的狀態。每次從編輯畫面開始，也避免「上次關掉了，這次打開什麼都拖不動」的困惑。預覽保留原本關閉時的畫面與輸出，所以 M9 的位元組恆等驗收和效能路徑（預覽時不做旁觀視角更新、不算 `obs ms`）都可以沿用。代價：頁面開啟就多一個 WebGL 畫面與每格的旁觀視角更新（M9 實測五個範例拖曳每格總計約 4–24 ms，在 100 ms 預算內）；想永遠只看作圖畫面的使用者每次開頁都要按一次「預覽」。

## D81 選取與「點選物體」旋轉中心統一：只有「點一下」才選取並（在點選物體模式）取旋轉中心，拖曳選取但不取；選取的物體也是視線的對象（修訂 M10 的點選物體規則；右窗維持 D79 的唯讀規則（Q1 已由使用者確認）；合約 §5.8.2、§5.8.6、§5.8.14，與 §5.7 實作註記「(M11, D81, D82)」）

- **規格**：規格 v0.3 §0 的修訂表、§3：規格寫兩個窗都能選取物體（本專案只採左窗，右窗維持唯讀，見決定 5）；點一下選取，拖曳選取並移動；點選物體模式的旋轉中心隨「點一下」取得；左窗的點擊順序為箭頭 > 圓環 > 垂直把手 > 物體 > 空白。本條修訂規格 v0.2 §5.4 與 M10 的做法：點選物體的旋轉中心原本由左窗的「點一下」物體取得，視線（旁觀視角的頂點視線）的對象固定是 `objects[0]`。
- **問題**：M10 的左窗在物體上按下會開始旁觀相機的環繞，所以「點一下物體」只可能發生在左窗，而且物體不能被拖動。M11 讓物體可拖，如果沿用舊規則，按下物體要同時決定三件事：是否選取、是否開始拖曳、是否取旋轉中心，三者互相打架——拖一個物體就會把旋轉中心換掉，畫面隨之跳動。另一方面，D79 把右窗（作圖畫面）定為唯讀；規格 v0.3 要求兩窗都能選取與拖曳，使用者在 Q1 回答「右窗拖動不做事，空白處的手勢維持惰性」，所以選取與拖曳只在左窗進行。視線對象固定為 `objects[0]` 時，選了別的物體，視線卻還畫在第一個物體上。
- **決定**：
  1. 一個手勢只有一種結局：按下物體的位移最大值 < 5 px（`CLICK_PX`）是**點一下**，選取該物體，若選單是「點選物體」再取它目前的邊界盒中心為旋轉中心（`P`）；位移 ≥ 5 px 是**拖曳**，選取並移動該物體，**不**取旋轉中心。在左窗點空白處清除選取，不動 `P`。新增物體時新物體成為選取，`P` 不變。
  2. 左窗的點擊順序改為箭頭 > 圓環 > **已選取物體**的垂直把手 > 物體 > 空白（旁觀環繞）。圓環與把手的命中優先於物體；在物體上按下不再開始旁觀環繞；點在空白處而位移 < 5 px 時視角回到按下前，並清除選取。
  3. 選取只在左窗進行（右窗完全唯讀，見 5），在兩種選單模式下都有效；選單只決定點一下之後取不取旋轉中心。切換選單到「點選物體」**不**取旋轉中心（沿用 M10 的規則，與選取了誰無關）。
  4. 旁觀視角的頂點視線（視線與光線）以**選取的物體**為對象，沒有選取時用 `objects[0]`；選取改變時重建旁觀幾何，不經核心。曲面物體仍不畫頂點視線。
  5. 右窗維持 D79 的唯讀規則（Q1 已由使用者確認）：所有手勢——含按在物體上的、點空白處的——都安靜地不做事，`#stage` 上沒有任何指標、滾輪或觸控監聽；選取、拖曳與點空白處清除選取都只在左窗進行。右窗只畫選取外框（介面，`pointer-events: none`），不接受輸入。D79 不被修訂。
  6. 選取只是網頁狀態：不在場景 JSON、不在復原堆疊裡，也不進任何輸出；選取框、垂直把手、標籤都是介面，下載的 SVG、JSON 在有無選取時逐位元組相同。
- **理由**：「點一下」與「拖一下」是兩種意圖：點一下是在說「這個」，拖一下是在說「把它移走」，後者不該順便換掉使用者另外設定的旋轉中心（D82）。用位移最大值而不是放開時的淨位移來分，輕微抖動的點擊不會讓物體移動，拖出去又拖回來的手勢也不會被當成點擊。選取成為視線的對象，選了什麼就看什麼，不必另外一個設定。D79 的取捨（右窗是穩定的結果畫面，不因手指一動就改視角）原封不動，右窗連物體也不接受手勢；物體在左窗編輯。使用者已確認右窗唯讀（Q1），因此右窗空白處的點擊（Q21）與觸控的 `touch-action`（Q19）都不再是問題。**待確認**：選單切到「點選物體」不取旋轉中心、「重新取中心」取選取的物體（Q22）；網頁以 `name（id）` 顯示（Q33）。代價：預覽時旁觀窗被隱藏，預覽中不能選取或移動物體（見 D83）；需要測試保證右窗在物體上也不做事。

## D82 旋轉中心是取值當下的點：新增、拖曳、刪除物體都不會移動它，「重新取中心」重取，「重設」改為「重設視角」（修訂 M10 的旋轉中心決定與合約 §5.7.7 的「Derived, never stored」；合約 §5.8.5、§5.8.6，與 §5.7 實作註記「(M11, D81, D82)」「(M11, D82, D86)」）

- **規格**：規格 v0.3 §0 的修訂表（共五處）、§3、§4.3：旋轉中心 `P` 是「設定當下取的那個點」；新增「重新取中心」按鈕；「重設」改為只重設視角（板子、旋轉中心、旁觀相機），不還原物體。修訂 M10 的做法：`P` 由 `rig` 依場景的邊界盒或所選物體的邊界盒**即時推算**（合約 §5.7.7 的「Derived, never stored」），重設把相機、旋轉中心與旁觀視角全部回到載入狀態，旁觀視角的取景點含場景中心與其地面點。D77 的不變量（旋轉中心沿 f 的深度永遠是 R）不變。
- **問題**：M10 的 `P` 隨場景推導，物體不能動所以一直成立。M11 一旦可以拖、加、刪物體，推導出來的 `P` 就會跟著動：拖著被當成旋轉中心的物體，整個板子與眼睛被帶著跑（眼睛對 `P` 是剛體運動）；加一個物體，場景中心改變，整個畫面跳動；刪掉物體，`P` 掉到別處。三種情況都是使用者沒要求的相機位移。另外「重設」若只是回到載入狀態，會與「還原物體」混淆，而且載入時的場景中心不等於編輯後的場景中心。
- **決定**：
  1. `P` 存在 `rig` 裡，不再從 stage A 推算。只有這幾件事會設定它：載入場景（stage A 邊界盒的中心）；選單切到「場景中心」（**目前**的邊界盒中心）；選單是「點選物體」時**點一下**物體（該物體目前的邊界盒中心）；新按鈕「重新取中心」；重設視角。新增、拖曳、垂直拖曳、刪除、選取、復原與重做物體步驟都不移動 `P`，包括被拖或被刪的正是取 `P` 的那個物體；工作階段每次編輯後只更新自己的中心、物體中心與頂點清單，**供下次取值用**。取值讓 `P` 移動時，平移 (a, b) 歸零、旁觀視角重新取景，並且不是復原步驟（M10 項目 10 不變）。
  2. 「重新取中心」依目前模式重取：場景中心模式取目前的邊界盒中心；點選物體模式有選取就取該物體目前的邊界盒中心，沒有選取就取目前的場景邊界盒中心。選取與「取旋轉中心的物體」可以不同（拖曳選取但不取），標籤顯示後者；被刪除的物體，標籤去掉名字，`P` 不動。
  3. 「重設」改名「重設視角」（元素 id `reset` 不變）：重設板子、旋轉中心與旁觀相機，**不**還原、新增或刪除物體，也不改選取。新的相機狀態是載入規則套在 `scene.camera` 與**目前**的場景中心，R 與 D 的夾限及提示重新計算，`scene_block = !clamped`，所以沒被夾限時畫面又是 `scene.camera` 的原樣；選單回到「場景中心」，旁觀相機回到 (55°, 28°) 並取景。重設是一個復原步驟（旋轉中心、選單或相機有變時才記）。
  4. 旁觀視角的取景點改為 `{E, Q}` 加上**場景邊界盒的八個角**、點光源與畫框四角，取代原本的場景中心與其地面點；物體編輯（新增、拖曳、垂直拖曳、刪除、復原與重做物體步驟）**不**重新取景，避免畫面在手下跳動；按「整體顯示」才依目前的邊界盒取景。
  5. 修訂範圍：本條取代 M10 對 `P` 的「推導、不儲存」說法（合約 §5.7.7、§5.7.8 項目 10、§5.7.9 點擊順序、§5.6.5 的 `旋轉中心：<物體 id>` 標籤，以及 M10 註記「Observer handles and their input」與「Review fixes (3)」），共六處；D77、D78 對 `R`、平移與滾轉的定義不變。
- **理由**：旋轉中心是使用者的「注視點」，應該是使用者設定的值，而不是隨場景變動的推導值——就像你在地圖上釘了一個點，之後在別處放東西，不該讓釘子自己動。取值當下的點讓編輯與視角完全解耦：拖物體時畫面只有那個物體動。想換注視點是明確的動作（點一下、重新取中心、重設視角）。載入規則套在目前的中心，是因為「回到 `scene.camera`」才是使用者對「重設視角」的期待，物體則是內容，不屬於視角。取景用邊界盒角點，是因為編輯過程中畫面不該動，而按「整體顯示」時需要一個不依賴頂點數量的包圍。**待確認**：重設視角的目標、選取保留與標籤（Q8，使用者已確認）；物體編輯不重新取景（Q9，使用者已確認）；復原重設只還原板子與旋轉中心、不還原旁觀相機（Q14，使用者已確認）；取 `P` 的物體被刪除後去掉名字（Q15）；切換到「點選物體」不取 `P`（Q22）。代價：`P` 不再自動保持在場景中心，大量編輯後可能離物體很遠，需要使用者按「重新取中心」。

## D83 水平拖曳、垂直把手與擦掠角後備：在拖曳平面上擷取抓取偏移，視線近乎水平時改以像素換算，垂直拖曳用與垂直線最近的點，右窗維持 D79 的唯讀規則（Q1 已由使用者確認），預覽時場景唯讀（Q2 已由使用者確認）（合約 §5.8.3、§5.8.4、§5.8.12、§5.8.14，與 §5.7 實作註記「(M11, D83)」；不修訂 D79，修訂 D80 的註記）

- **規格**：規格 v0.3 §4（拖曳）、§4.4（算圖預算）、§9（退化情形）：水平拖曳是把指標射線與抓取點所在的水平面相交；射線接近水平時改用像素換算；垂直方向用把手；放開時吸附到 0.1 m 格線，按住 Alt 暫停吸附。規格 v0.2 §5.9／D79：右窗唯讀；D80：預覽時板子不能拖。規格 v0.3 的右窗拖曳與右窗射線不採用（使用者 Q1）。
- **問題**：直接把射線與 `z = 0` 求交，在物體頂面上抓的點與地面的點高度不同，物體會在按下的瞬間跳一下；視線近乎水平（例如 demo 預設眼高 0.9 m 的平視）時，射線與水平面的交點極遠或在視點後面，一動就飛出去，而且在越過 5° 時如果換演算法，物體會跳；垂直方向不能用同一個平面，因為水平射線與垂直線的交點不存在；取整若寫成 `Math.round(v/0.1)*0.1` 會得到 `0.30000000000000004` 之類的數，場景檔與位元組一致性都會受影響；載入時超出 ±50 m 的物體，如果夾限在按下時就把它拉回來，會造成沒有拖動就位移。D80 的「預覽不能拖板子」沒有預見物體編輯：預覽時旁觀窗被隱藏，而物體只能在旁觀窗選取與拖曳，右窗又是唯讀（D79），所以預覽中沒有任何地方能選取或移動物體。
- **決定**：
  1. **水平拖曳**：按下時取射線打到的表面點 `h₀`，拖曳平面是 `z = h₀_z`，抓取偏移 `δ = (p₀_x − h₀_x, p₀_y − h₀_y)`；每次移動，射線與該平面的交點加上 `δ` 就是新的 `(x, y)`，`z_b` 逐位元照抄、不夾限。射線的 `t` 不是有限的正數或 `> 200` 時跳過該次更新，物體留在原處。
  2. **擦掠角後備**：按下當下，若 `|d₀_z| < sin 5°`，或交點在射線後面，則整個拖曳都改用像素換算：`k = ((h₀ − e₀)·f_c) / f_px`（抓取點的**相機深度**除以每像素焦距，即規格的「物件深度 / 每像素焦距」；若用歐氏距離 `|h₀ − e₀|`，偏離光軸 θ 的點會多走 `1/cos θ` 倍），先把螢幕位移去掉滾轉：`w = Δx·r − Δy·u`、`Δx' = w·right₀`、`Δv' = w·up₀`（`r`、`u` 是按下時含滾轉的畫框右與上，`right₀`、`up₀` 是合約 §5.7.3 的水平預設基底），再取 `(x, y) = (p₀_x, p₀_y) + k·(Δx'·r_g + Δv'·f_g)`，`r_g` 是 `right₀` 的水平分量、`f_g` 是相機前向在地面上的投影（正上下看時改用 `up₀` 的投影）。`r_g ⊥ f_g`，所以任何滾轉角下這個對應都是滿秩的；滾轉為 0 時就是 `k·(Δx·r_g − Δy·f_g)`：往右拖往 `r_g` 走，往下拖靠近、往上拖推遠。若直接用含滾轉的右向量，滾轉 90° 時右拖與下拖都沿前向，物體無法橫移。**是否後備在按下時決定一次，拖曳中不切換**，所以射線越過 5° 時物體不會跳。旁觀視角沒有滾轉，所以網頁中去滾轉等於不動；公式保留滾轉項，是因為純函式以含滾轉的畫框測試。旁觀視角的預設仰角是 28°，窗格上緣也在水平線下 8°，所有按下都走正常模式；仰角低於約 25° 時窗格上半部的按下會落在後備。越俯視越接近「抓的點跟著指標」。
  3. **完成值**：對 `x`、`y` 各別：吸附時 `Math.round(v·10)/10`，否則 `Math.round(v·1e4)/1e4`；然後夾在 `[min(−50, v₀), max(50, v₀)]`，最後 `v + 0` 去掉 `-0`。夾限只作用在**正在移動的座標**，永遠不在按下時移動物體：載入時超出 ±50 m 的物體只能被往內拖，不能往外推。因為夾限在取整之後、邊界可以是 `v₀`，載入時不在格點上又超出 ±50 m 的座標在吸附下往外拖，結果就是 `v₀` 本身，不在 0.1 m 格點上；這是吸附結果唯一不在格點上的情形（垂直把手的 `z_b0` 同理）。吸附由「吸附」勾選且**這次移動事件**沒有按 Alt 決定。位移 `< 5 px` 的手勢是點一下，不移動物體（D81）；越過門檻的那次移動，位置由按下後的總位移重算，物體不會落後一個門檻。
  4. **垂直把手（只在旁觀視角）**：選取物體的世界邊界盒頂面中心 `b` 往上畫一條長 `max(clamp(0.6·高, 0.3, 1.0), L₃₆)` 公尺的箭頭，`L₃₆` 是在旁觀相機中投影**恰為 36 px** 的長度（合約 §5.8.4 的閉式解；只用 `36·深度/f_px` 在預設仰角 28° 時只有 32.5 px），尖端有圓盤可抓；按下時垂直線是**把手自己的那一條**，通過世界邊界盒中心 `(c_x, c_y, 0) + s·ẑ`（規格 v0.3 §4.2 寫通過錨點；錨點不在盒中心時——例如三角柱、多邊形原點偏離盒中心的稜柱、傾斜物體、網格——只有把手的線能讓尖端留在指標下，而位移一樣是純垂直），指標射線與這條線的最近點給出 `s`，`z_b ← z_b0 + (s − s₀)`；射線近乎垂直（`|1 − β²| < 1e-6`）或最近點在眼睛後面時跳過該次更新。完成值：吸附或 1e-4 取整，夾在 `[min(0, z_b0), max(50, z_b0)]`，然後**貼地**：`|z_b| < 0.02` 一律變 0（含 Alt），地面因此是黏的；埋在地下的物體（`z_b0 < 0`）按下時不被推到 0。錨點因類型而異（球是最低點）。
  5. **右窗與預覽**：右窗維持 D79 的唯讀規則（Q1 已由使用者確認）：所有手勢——含按在物體上的——安靜地不做事、不被阻止，沒有水平拖曳，也沒有垂直把手；沒有右窗射線，不使用作圖相機記錄 `rec` 來命中物體。**預覽時場景唯讀**（Q2 已由使用者確認，理由是右窗本來就不能編輯）：旁觀窗被隱藏，因此不能選取或移動物體，垂直把手不可用；物件庫的分頁與側欄隱藏（展開著的側欄在進入預覽時收合）、Delete／Backspace 不做事且選取晶片（含刪除鈕）隱藏、復原與重做（按鈕與 Ctrl／⌘+Z、Ctrl／⌘+Shift+Z，板子項目也一樣）不做事。這修訂 D80 註記 (2) 的控制項清單：預覽時 復原 也不可用。選取在預覽往返之後保留，外框仍畫在右窗。進入預覽在手勢進行中被拒絕（與握著把手時相同），進入時也取消尚未成為手勢的按下。
  6. **算圖**：每個動畫格最多重算一次（`validate_scene`、stage A、B、C、SVG），拖曳時 `umbra = false`、`hidden_lines = false`，放開後那一格才完整；若前一次拖曳模式的整格重算超過 50 ms，這次手勢改為預覽模式——不跑 A、B、C，只在 `#sel-overlay` 畫物體線框，放開時一次完整重算；決定在按下時做一次，拖曳中不切換。目標：不超過 10 個基本形的場景每次拖曳更新 < 33 ms，記在 `web/README.md`，**不設閘**。
- **理由**：在抓取點所在高度的平面上求交，加上抓取偏移，物體在按下的瞬間不會跳，而且指標「抓住」的是原來那一點。擦掠角本來就是這個方法的奇異處，與其在一個閾值兩邊用兩套公式，不如讓整個手勢只有一套，並在按下時決定；5° 與 `t ≤ 200` 都是為了讓錯誤只有「這次沒更新」而不是「物體飛走」。取整寫成「乘 10 再除 10」是因為 `0.3` 這個字面值是 `round(3)/10` 的結果，場景檔因此乾淨；`-0` 會出現在輸出的 JSON 裡，必須去掉。只夾限正在動的座標、不在按下時動物體，符合「沒有動手就沒有位移」。垂直方向用「與垂直線最近的點」而不是平面，因為這個問題在近乎水平的視線下仍然有解。右窗維持 D79 的唯讀規則，連物體也不接受手勢（Q1，使用者確認），物體只在左窗編輯；預覽時旁觀窗隱藏、右窗不能編輯，乾脆整個預覽都不給編輯（Q2，使用者確認），也避免在預覽中復原一個看不見的操作。拖曳時的線框預覽模式讓大場景（例如幾萬個三角形的網格）仍能跟手，輸出永遠不吃到線框。**待確認**：第二根手指取消尚未位移 5 px 的拖曳，零個復原步驟（Q18，使用者已確認）；點擊的位移與記錄時機（Q20）；各類型的錨點與把手公式（Q25、Q28）；夾限與貼地（Q26）；預覽模式的門檻決定（Q29）；拖曳中的畫面變動讀值也計入物體拖曳（Q30）。

## D84 物件庫的預設物件、放置與 id 規則：收合的側欄覆蓋在窗格上、八個預設物件以 1e-4 字面值存放、放在眼睛看向地面的那一點並避開重疊、id 取最小未用的編號（合約 §5.8.7、§5.8.8、§5.8.9）

- **規格**：規格 v0.3 §2（側欄）、§5.1（八個預設物件）、§5.2（放置）、§5.3（id 與顯示名）：側欄預設收合，展開時覆蓋窗格而不推動它們；磚塊是 64 px 縮圖加一行名字；點磚塊就新增物件並選取；新物件放在視線落地點並避免重疊；id 為 `前綴_n`。
- **問題**：側欄若把窗格推開，畫布尺寸改變會讓兩個窗格重新取樣、畫面跳動，而且窄螢幕根本沒有空間；預設多邊形若用 `cos`／`sin` 在執行時算，存進場景檔的是 `0.20000000000000007`、`4.9e-17` 這類數，與 1e-4 取整的拖曳位置不一致，兩個實作也可能差一個位元；三角柱的頂點方向規格沒有指定；頂點朝 `±y` 時，放在 `x = 0`（內建範例的相機與光源所在的鉛直面，也是三角柱的預設放置位置）會讓核心略過一個作圖檢查（`CONSTRUCTION_CHECK_SKIPPED`，無害但惱人）——但這個警告是**位置性**的，任何預設物件只要有頂點或輪廓點落在通過眼睛與光源的鉛直面上都會出現（方塊在 `x = ±0.5`、高柱在 `x = ±0.3`、六角柱在 `x = ±0.2`、`±0.4`，都在 0.1 m 格點上；球與圓錐在預設目標 `(0, 15, 0)`；頂點朝 `+x` 的三角柱在 `x = 0.2887`、`−0.5774`）。放置位置若用盒子中心而不是錨點，球（錨點是最低點）與盒子的行為不同；新物件落在別的物件上則看不出有新增；id 若只比對物件，可能與燈或接收面撞名，也可能撞到保留字；刪掉 `box_1` 之後再新增，若不重用編號，編號會一直往上漲。
- **決定**：
  1. **側欄**：左緣有一個垂直的「物件庫」分頁；`#lib` 預設收合（頁面開啟、每次載入場景後），狀態不儲存；展開時寬 232 px、**覆蓋**在畫布與標籤之上，不推動窗格、不改任何畫布的大小；收合時隱藏並 `inert`，磚塊不在 Tab 順序。窄螢幕（視窗寬 < 880 px）寬度 `min(80%, 280px)`，點側欄外面會關閉，**而且那一下被吃掉**（不啟動手勢、不改選取）；新增後在窄螢幕自動關閉，寬螢幕保持展開以便連續新增。關閉時若焦點在側欄內，焦點回到分頁。**收合只有兩種方式**（Q3 已由使用者確認）：側欄標題列的收合鈕 `#lib-close`（`aria-label`「收合物件庫」），以及 Ctrl+Shift+L（macOS 為 ⌘⇧L，焦點在文字輸入欄時不攔截，與 Delete、Ctrl+Z 相同；預覽時不做事；處理時呼叫 `preventDefault`；瀏覽器或作業系統在某些環境可能保留這組鍵，所以收合鈕與分頁鈕仍是後備）；分頁鈕負責展開，並帶 `aria-keyshortcuts="Control+Shift+L"`。**Esc 不展開也不收合物件庫**，規格 v0.3 §2、§3 的「Esc 收合物件庫」不採用。窄螢幕的「新增後自動收合」與「點側欄外收合」保留（它們不是 Esc）。預覽時分頁隱藏、側欄 `inert`，進入預覽時展開著的側欄收合。
  2. **八個預設物件**（名稱、型別、參數、id 前綴）：方塊（`box`，`size` `[1.0, 1.0, 1.0]`）、木箱（`box`，`[1.2, 0.9, 0.7]`）、高柱（`box`，`[0.6, 0.6, 1.8]`）、圓柱（`cylinder`，半徑 0.3、高 1.2）、球（`sphere`，半徑 0.5）、圓錐（`cone`，半徑 0.4、高 1.0）、三角柱（`prism`，邊長 1.0 的正三角形，高 1.0）、六角柱（`prism`，外接圓半徑 0.4，高 1.0）。多邊形**直接存成 1e-4 的字面值**，逆時針，形心在 `(0, 0)`，不在執行時用三角函數計算；三角柱的頂點在 **`+x`**（規格 v0.3 §5.1 沒有指定），在試過的位置（`(0, 10.5)`、`(0, 5)`、`(0, 3)`、`(0.1, 3)`、`(0.4, 3.1)`）驗證過：Python 與 TS 的 SVG 位元組相同、沒有警告（在其他位置仍可能出現上述位置性警告）。八個預設物件都通過核心驗證。位置為 `[x, y, 0.0]`、旋轉為 `[0.0, 0.0, 0.0]`。縮圖是內嵌 SVG（`viewBox="0 0 64 64"`），`currentColor` 描線，跟隨亮暗主題。庫只建立這五個基本形，不含網格。
  3. **放置**：目標 `T`：視線向下（`f_z < −sin 2°`）且落地距離 `0 < t ≤ 40` 時取眼睛看向的地面點，否則取旋轉中心的 `(P_x, P_y, 0)`；**錨點**（不是盒子中心）放在 `T`，`z_b = 0`。避讓：候選物的占地與每個既有物件的世界邊界盒（含各種高度）在 x、y 兩方向的間距都 `< 0.1 m` 就算重疊，重疊時沿著滾轉前的相機右向在地面上的投影，每次移動 `占地沿該方向的寬度 + 0.2 m`，最多 8 次，還重疊就留在最後的位置；有界的接收面（牆、板）不避讓。然後依「吸附」取到 0.1 m 或 1e-4 m、夾在 ±50 m、去掉 `-0`；吸附後不再重跑避讓。新物件附加在 `objects` **最後**、成為選取，不動旋轉中心與旁觀取景。
  4. **id 規則**：`next_id(前綴, used)` 回傳 `前綴_n`，`n` 是使 `前綴_n` 不在 `used` 裡的最小整數 `n ≥ 1`，`used` 是目前場景中**所有**物件、燈與接收面的 id（精確、區分大小寫）。五個前綴固定為 `box`、`cylinder`、`sphere`、`cone`、`prism`，因此結果不會含 `.`、不會等於保留字 `hidden`、`core`、`umbra`。比對燈與接收面比核心嚴格（核心只要求接收面 id 不同於物件 id），這樣 id 可以安全地當作點名的字根與子圖層名。**釋出的編號會重用**：刪掉 `box_1` 再新增方塊，又是 `box_1`——因為復原堆疊是後進先出，新增動作會清掉重做堆疊（D86），被刪的 `box_1` 只有在新的那個被復原之後才可能回來。
  5. **顯示名**：磚塊的名字不寫進場景 JSON；工作階段另存一個 `id → 名字` 的旁表，新增時記錄、刪除的紀錄帶著名字、復原時放回；沒有名字的物件（載入的或其他）顯示 id；選取條顯示 `名字（id）`，沒有名字時只顯示 id。
- **理由**：覆蓋式側欄讓畫布永不重新取樣，也讓窄螢幕可用；窄螢幕點外面關閉的那一下被吃掉，避免「關側欄的同時選到下面的物體」。1e-4 字面值讓存檔乾淨，也讓兩個實作讀到完全相同的位元組；三角柱頂點取 `+x`，主要是與六角柱「第一個頂點在 `+x`」一致；它只在預設放置位置 `x = 0` 避開那個無害的位置性警告，其他預設物件在格點上一樣會碰到，所以這不是預設物件本身的性質。以錨點而非中心放置，才與拖曳的錨點定義（D83）一致，球也不例外。最小未用編號最容易預測，也不會讓編號無限增長；比對所有 id 而不是只比對物件，是為了讓點名與子圖層名永遠不撞。顯示名不進場景檔，是因為核心的 `id` 就是唯一的名字，額外的欄位會成為合約變更。**待確認**：八個預設的多邊形字面值與三角柱頂點（Q13）；放置的細節——錨點放在 `T`、右向向量取滾轉前、`u` 方向避讓、±50 m、接收面不避讓（Q27）；窄螢幕點外面被吃掉、顯示刪除提示、以視窗寬度為斷點（Q34；收合時的 `inert` 與關閉後焦點回分頁是 Q34 第 4 項的預設）；顯示名旁表（Q15、Q33）；網格物體可選取、可拖、可刪但不在庫裡（Q24）。

## D85 至少保留一個物件：最後一個物件不能刪除，按鈕停用並顯示文字，Delete 鍵顯示相同提示（合約 §5.8.10）

- **規格**：規格 v0.3 §6：選取後按 Delete 或 Backspace、或按選取條上的「刪除」就刪除；場景至少要有一個物件。核心驗證（合約 §2.0）要求 `objects` 非空。
- **問題**：刪掉最後一個物件會讓場景 JSON 不合法，驗證擲出 `SceneError(field="objects")`，頁面就會停在一個錯誤畫面，原來的內容也已經丟掉；若按鈕只在懸停時顯示提示，觸控裝置永遠看不到理由。Delete／Backspace 在文字欄位裡是編輯文字的鍵（方程式欄位就是文字欄位），攔截它們會破壞輸入；macOS 的刪除鍵是 Backspace；輸入法組字中的 Backspace 也不能被吃掉。
- **決定**：
  1. 物件總數 `≤ 1`（含網格物件）時，選取條上的「刪除」按鈕 `disabled`，並**以可見文字**顯示「場景至少要有一個物件」；按 Delete／Backspace 不刪除、在 `#notices` 顯示同樣的文字；被拒絕的刪除不記入復原。
  2. 有選取、沒有按 Ctrl、Meta、Alt，且不在輸入法組字（`isComposing`）時，Delete 與 Backspace 刪除選取的物件。焦點在文字類目標（`<textarea>`、`contenteditable`、`type` 為 `text`、`search`、`number`、`email`、`url`、`tel`、`password` 或缺少、未知的 `<input>`）時**不攔截**，瀏覽器照常處理；範圍滑桿、勾選框、按鈕、`<select>`、檔案欄位不算文字，快捷鍵照樣作用。只有快捷鍵真的有作用（刪除、或被拒絕的刪除）時才呼叫 `preventDefault`。
  3. 刪除會移除該物件（其他物件的順序不變）、清除選取、把顯示名放進復原紀錄、**不**動旋轉中心與取點物體的設定（D82），結束「這次拖動畫面變動」的量測（頂點清單變了），並記一個含**原索引**的刪除項目（D86）。手勢進行中（拖曳、握著把手）刪除指令被忽略。
  4. 窄螢幕上沒有鍵盤，所以選取條的「刪除」按鈕是觸控的入口，並在選取時一直可見。
- **理由**：核心不接受空場景，是檢查在輸入端做好於擲出例外之後補救；用可見的文字解釋為什麼不能刪，比靜默忽略好，也不會讓觸控使用者摸不著頭緒。快捷鍵不攔截文字欄位，是為了不破壞方程式欄位的輸入；範圍滑桿、勾選框等不是打字的地方，所以在它們上面按刪除鍵仍然有用，使用者才不必先點空白處。**待確認**：快捷鍵的焦點規則與手勢進行中指令被忽略（Q17）。

## D86 物件編輯併入同一個復原堆疊：新增、刪除、移動都是步驟，有重做；選取、物件庫、重新取中心、預覽不是步驟（修訂 M10 的復原規則；合約 §5.8.11，與 §5.7 實作註記「(M11, D86)」「(M11, D82, D86)」）

- **規格**：規格 v0.3 §3、§7：物件編輯可以復原與重做，與板子的操作共用同一個堆疊；快捷鍵 Ctrl／⌘+Z 與 Ctrl／⌘+Shift+Z；Esc 依序處理（Esc 收合物件庫的部分不採用，見決定 6）。修訂 M10 的做法：復原堆疊只記板子的步驟（合約 §5.7.8 項目 13 與 D79 註記 (4)），沒有重做，也沒有任何鍵盤快捷鍵；「重設」把一切回到載入狀態。
- **問題**：如果物件編輯有自己的堆疊，使用者就要記住「這一步是板子還是物體」，按一次復原到底撤的是哪一個無法預期。整份場景做快照在大網格場景太貴（含 49 900 個三角形網格的場景，50 份深拷貝約 570 MiB，一份約 6–11 MiB），而且復原物件步驟若連板子也一起還原，使用者剛調好的滑桿就沒了。刪除之後再復原，如果插在陣列最後面，每個多物件場景的位元組都會改變（物體順序影響頂點編號與輸出）。拖曳手勢進行中若允許復原，鍵盤復原會彈出尚未完成的那一項。重做堆疊若沒有清除規則，之後又調了滑桿，重做一個舊的板子步驟會覆蓋它。
- **決定**：
  1. **一個堆疊**：仍然是 `UNDO_MAX = 50` 個項目，最舊的先丟。項目是標記聯集（不是整份場景快照）：`board {before, after}`（M10 的各步驟，復原時保留目前的 `P`）、`reset {before, after, pivot_before, pivot_after}`（重設視角，復原連旋轉中心與選單一併還原，D82）、`add {index, obj, name}`、`delete {index, obj, name}`（插回**同一筆紀錄**到**原索引**）、`move {index, id, before, after}`（一次水平拖曳或垂直把手拖曳，**放開時**才記，沒有改變就不記）。物件項目只還原紀錄，不碰板子；板子項目只還原板子，不動物體——復原物體的操作不會還原滑桿。
  2. **重做**：新增 `#redo` 按鈕，Ctrl／⌘+Z 復原、Ctrl／⌘+Shift+Z 重做（`Ctrl+Y` 不綁定），快捷鍵遵守 D85 的焦點規則。載入場景會清除兩個堆疊；失敗的載入保留舊場景與堆疊。**重做在以下情況清除**：記下任何新項目，或任何不是復原／重做的實際變動——相機（例如滑桿）、旋轉中心或選單、物體；選取、物件庫、旁觀相機、切換與預覽不清除。
  3. **位元組完全還原**：紀錄不可變、以參照插回原索引，所以復原刪除（或新增、移動，再重做）之後，文件文字與 SVG 文字與操作前逐位元組相同，相機與 `scene_block` 不受物件項目影響。堆疊操作若發現陣列與項目不符，視為程式錯誤：清除兩個堆疊、場景保持原狀。
  4. **不是步驟**：選取、物件庫的開合、「重新取中心」、旋轉中心選單與取點、滑桿（沿用 M10）、旁觀相機、各種切換、預覽、下載。復原或重做物件項目之後，選取跟著該項目所作用的物體（新增的復原清除選取，刪除的復原選取還原的物體，移動的復原與重做選取被移動的物體）；板子與重設項目保留選取，已不存在的 id 清除。
  5. **手勢進行中**（環、箭頭、把手、垂直或物體拖曳）復原、重做、刪除、新增、重設視角、重新取中心被忽略，按鈕停用。復原、重做、刪除、新增在預覽時也不可用（預覽時場景唯讀，D83）；重設視角與重新取中心照 M10。
  6. **Esc**（Q3 已由使用者確認）：每按一次只做一件事：方程式欄位有焦點時是它自己的 Esc（丟掉輸入，不再往外，與 D80 相同）；否則預覽中就返回編輯（選取在往返後保留）；否則在編輯畫面清除選取。Esc **永遠不展開或收合物件庫**（物件庫以收合鈕或 Ctrl+Shift+L 收合，見 D84）；拖曳進行中 Esc 不做事。
  7. 一次物件復原或重做是**一次完整重算**（10 個基本形約 17 ms）；板子的復原仍然只重算 B、C。核心、擴充文件與一致性測試集不變。
- **理由**：一個堆疊符合使用者的直覺——「復原」就是撤銷最近做的一件事，不論它是調視角還是移物體；項目只記差異而不是快照，才負擔得起大網格；物件項目與板子項目互不影響，是因為它們改的是不同的狀態，一起還原會吃掉使用者沒要求撤銷的事。原索引加不可變紀錄，是位元組一致性的唯一保證。重做的清除規則簡單地說就是「人做了新事情，舊的未來就不存在了」，滑桿也算，所以不會出現靜默的覆蓋。Esc 的順序是使用者定的：預覽中就離開預覽，編輯時才清除選取，物件庫完全不歸 Esc 管，免得一個鍵同時負責三件不相干的事。**待確認**：復原重設只還原板子與旋轉中心（Q14，使用者已確認）；復原後選取跟著動作的物體（Q15）；重做的清除範圍（Q16）；手勢進行中指令被忽略與快捷鍵焦點規則（Q17）；點一下的記錄時機（Q20）。代價：復原項目種類多了，需要測試保證「復原一個刪除是位元組相同」與「物件復原不動板子」。
